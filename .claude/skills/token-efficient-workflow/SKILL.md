# کار کم‌مصرف در Label Mod Core

`CLAUDE.md`، ADRها و `.claude/rules/` بر این Skill اولویت دارند. این Skill
فقط **مسیر رسیدن** را ارزان می‌کند؛ سخت‌گیری تست، امنیت و صحت مالی را هرگز
کم نمی‌کند. جایی که ارزانی و صحت مالی تعارض دارند، صحت برنده است.

برای تئوری عمیق (KV-cache، observation masking، partitioning) به Skill
`context-engineering-suite` برو. اینجا فقط انضباط عملی است — تکرارش نکن.

## ۱. اول محدوده، بعد کار

- در یک تا سه جمله بنویس چه چیزی عوض می‌شود و کدام فایل‌ها محتمل‌اند.
- اگر محدوده مبهم است **یک سؤال بپرس**، نه اینکه مخزن را بگردی تا حدس بزنی.
- کار محدود، اسکن محدود. برای یک تابع در `sales`، کل `db/` را نخوان.

## ۲. جست‌وجوی هدفمند، نه اسکن کامل

- با `rg` روی نام دقیق (تابع، ستون، کلید تنظیم) شروع کن، نه با خواندن پوشه.
- `rg -l` برای یافتن فایل، بعد `rg -n` با Context کم برای دیدن خط‌ها.
- فهرست فایل با `git ls-files <زیرمسیر>` بگیر، نه با خواندن محتوای همه.
- برای کار روی تغییرات جاری: `git status --short` و `git diff --stat` اول،
  بعد `git diff -- <فایل>` فقط برای همان‌ها.
- هرگز کل `db/migrations/` یا کل `apps/` را «برای شناخت» نخوان.

## ۳. خواندن گزینشی

- فایل بزرگ را با بازه خط بخوان (`sed -n '120,180p'`)، نه کامل.
- برای نسخه جاری یک تابع SQL از `\sf <schema>.<name>` استفاده کن — نه
  خواندن هر مهاجرتی که آن را `CREATE OR REPLACE` کرده.
- **فایلی را که در همین Session خوانده‌ای دوباره نخوان** مگر خودت عوضش
  کرده باشی. Edit موفق یعنی تغییر اعمال شد؛ برای اطمینان بازخوانی نکن.
- نتیجه‌ای را که قبلاً در همین گفت‌وگو گرفته‌ای دوباره استخراج نکن.

## ۴. خروجی‌های طولانی را قبل از Context فیلتر کن

- Log و خروجی تست را به فایل بده و فقط خلاصه را بخوان:
  `... > /tmp/x.log 2>&1; tail -30 /tmp/x.log` یا `grep -E 'FAIL|ERROR'`.
- خروجی `ops/db.sh test` طولانی است — اول دنبال خط‌های شکست بگرد.
- از `| head`، `| wc -l` و `--stat` به‌جای چاپ کامل استفاده کن.
- خروجی خام حجیم را در گزارش به کاربر نقل نکن؛ فقط یافته را بگو.

## ۵. تست: هدفمند اول، کامل آخر

- اول تست مرتبط با همان تغییر را اجرا کن (مثلاً فقط `db/test/costing.sql`).
- `ops/db.sh test` و `pnpm check` کامل را برای **پایان کار** نگه دار.
- این ترتیب سرعت است، نه تخفیف: قبل از اعلام «تمام»، مجموعه کامل باید سبز
  شده باشد و خروجی‌اش را دیده باشی.

## ۶. گزارش بدون تکرار

- تحلیل و گزارشی را که قبلاً داده‌ای بازنویسی نکن؛ به آن ارجاع بده.
- فقط دلتا را بگو: چه چیزی از آخرین گزارش تا حالا عوض شد.
- گزینه‌هایی که دنبال نمی‌کنی را فهرست نکن.

## ۷. مدل، Effort و Subagent

- **پیشنهاد بده، خودت عوض نکن.** تغییر مدل تصمیم کاربر است.
- کار عادی (اصلاح UI، تست، مستندات، refactor کوچک): Sonnet با Effort متوسط.
- معماری، امنیت، همزمانی و قفل، منطق مالی و دفتر کل: Opus با Effort بالا.
- Agent Team، `/loop` و Subagent پرمصرف را **بدون اجازه صریح کاربر** اجرا
  نکن؛ اول بگو چرا لازم است و چه هزینه‌ای دارد.

## ۸. مدیریت طول گفت‌وگو

- وظیفه طولانی که هنوز همان موضوع است: `/compact` را پیشنهاد بده.
- موضوع کاملاً نامرتبط: Chat جدید یا `/clear` را پیشنهاد بده.
- پیشنهاد بده و منتظر بمان — خودت گفت‌وگو را پاک نکن.
