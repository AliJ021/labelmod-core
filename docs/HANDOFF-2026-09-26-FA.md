# تحویل ادامهٔ Labelmod — ۲۶ سپتامبر ۲۰۲۶

این سند برای ادامه در Codex Cloud است. وضعیت را از GitHub و سرور دوباره بخوان؛ هیچ درصد یا ادعای «صددرصد بدون مشکل» از این سند برداشت نکن. هدف این توقف، حفظ کار به‌علت محدودیت مصرف هفتگی کاربر است، نه پایان پذیرش محصول.

## کار پیاده‌شده در این شاخه

### صندوق و فاکتورها

- ورودی واحد «نام، کد یا بارکد محصول»؛ نام به محصول مادر و انتخاب رنگ/سایز می‌رسد؛ بارکد دقیق همان تنوع را اضافه می‌کند. نرمال‌سازی فارسی/عربی و جلوگیری از جایگزینی نتیجه با پاسخ جست‌وجوی قدیمی.
- کنترل مجموع تعداد کالا در سطرهای پیش‌نویس نسبت به موجودی قابل‌فروش هنگام افزودن، تغییر تعداد و پیش از وجه، در سرور و تراکنش؛ کنترل نهایی حفظ شده و رزرو موجودی اضافه نشده است.
- صف و پیش‌نویس به هویت، شعبه، انبار و شیفت مقیدند. اسکن با پاسخ نامعلوم، کلید و payload اصلی را نگه می‌دارد. قفل مرورگر و هماهنگی دو تب از جایگزینی عملیات نامعلوم جلوگیری می‌کنند.
- مرکز فاکتورها با صفحه‌بندی سرور، وضعیت/شعبه/تاریخ/جست‌وجو، ثبت‌کننده و نهایی‌کننده، ادامهٔ پیش‌نویس مالک در شیفت باز و چاپ احراز‌شده. سابقهٔ بی‌شاهد با هویت حدسی پر نشده است.
- آستانهٔ نیازمند رسیدگی برای پیش‌نویس، پیش‌فرض ۲۴ ساعت؛ لغو یا حذف خودکار ندارد. «ذخیره و فروش جدید» از لغو جداست.
- گزارش فروش کاربر با مبنای ثبت‌کننده/نهایی‌کننده. اسنپ‌پی، ثبت دستی با مرجع و حساب تسویهٔ معتبر، پرداخت ترکیبی و گزارش مستقل است؛ درگاه واقعی اسنپ‌پی نیست و بدون تنظیم معتبر فعال نمی‌شود.

### رابط مشترک

- React/Vite حفظ شده؛ منوی راست دسکتاپ، ناوبری پایین موبایل و «بیشتر»، نشانی مستقل صفحات/زیرصفحات و بخشی از فیلترها، جست‌وجوی قابلیت‌های مجاز.
- سطوح شفاف در کنترل‌ها و سطوح خوانا برای اطلاعات مالی، تم روشن/تیره، کاهش حرکت/شفافیت، مرز خطای بخش‌ها با امکان برگشت به ناوبری.
- دسترسی آشکارتر به لیبل، چاپ فاکتور، موجودی، PIN و تنظیمات؛ کد قبلی SMS MFA و ملی‌پیامک حفظ شده است.
- README، CLAUDE و `docs/WEB-WORKSPACE-AUDIT.md` به‌روزرسانی شده‌اند. سند ممیزی فهرست اولیهٔ صفحات و API را دارد؛ همهٔ سطرهای آن به معنی پذیرش عملیاتی نیستند.

### امنیت ثبت سند و بکاپ

- migration `082_posting_scope_serialization.sql`: بستن گروه‌های سند از HTTP محدود به شعب مجاز؛ آرایهٔ خالی یعنی هیچ شعبه، NULL فقط در مسیر مورد اعتماد یعنی همه. wrapper دوآرگومانی زمان‌بند حفظ شده است.
- قفل اشتراکی گروه سند هنگام نهایی‌سازی تا پایان تراکنش نگه داشته می‌شود؛ بستن گروه منتظر می‌ماند و سناریوی ترتیب معکوس هم آزمون دارد. بازبینی مستقل پیش و پس از اصلاح انجام شد و بازبین مورد مشخص جدید گزارش نکرد.
- migrations جدید 079 تا 082 افزایشی‌اند: فضای فاکتورها، اسنپ‌پی، مجوز بکاپ، مرز شعبه/هم‌زمانی ثبت سند.
- کد اولیهٔ مدیریت بکاپ/restore مستقل، API محدود، رابط وب و مستندات در شاخه هست. بکاپ امضاشدهٔ همین سامانه، احراز مجدد و عامل دوم مدیر سراسری، سازگاری، rehearsal مالی، توقف نویسنده‌ها، بکاپ تازه، قفل عملیات، وضعیت خارج DB، swap/rollback و ابطال نشست‌ها طراحی/پیاده شده‌اند.
- **سرویس مدیریتی بکاپ روی سرور نصب یا فعال نشده و پذیرش عملیاتی آن کامل نیست.** موفقیت تست واحد/PG اجازهٔ اجرای restore اصلی نیست. راهنمای `docs/WEB-BACKUP-RESTORE.md` را بخوان و موارد باز پایین را بررسی کن.

## استقرار فعلی و محدودیت اطلاعات زیرساخت

نسخهٔ جدید با اجازهٔ کاربر روی محیط تست مستقر شد. پیش از استقرار بکاپ و rehearsal ارتقای یک کپی مستقل انجام شد، checksumهای ۸۲ migration موجود تطبیق داشت، سپس نویسنده‌ها متوقف و بکاپ تازه گرفته شد. migrations 079–082 و نقش محدود برنامه اعمال شدند.

**checkout قدیمی روی سرور معرف نسخهٔ در حال اجرا نیست.** استقرار جدید از release مستقل و compose override استفاده می‌کند. اجرای compose up/build از checkout قدیمی ممکن است نسخهٔ تازه را برگرداند. پیش از هر انتشار، imageهای running، mountها و override فعال را به روش فقط‌خواندنی شناسایی کن. secrets خروجی compose config را منتشر نکن.

جزئیات میزبان، اثر انگشت SSH، مسیرهای خصوصی بکاپ/rollback و شواهد عملیاتی عمداً در مخزن نیستند. این اطلاعات در فایل محلی جداگانهٔ `LABELMOD-PRIVATE-OPERATIONS-HANDOFF-20260926.md` نزد کاربر نگهداری شده‌اند؛ فقط اگر کار زنده لازم شد از او روش دسترسی امن را بگیر. نبود آن فایل مانع ادامهٔ کد و CI نیست. هیچ رمز یا بکاپی داخل این تحویل قرار ندارد.

کد runtime نسخهٔ مستقر همان candidate این شاخه است؛ پس از بسته‌بندی آن، fixture تست posting، تست دو تب و اسناد تغییر کردند. برای release بعدی از commit دقیق image بساز؛ تغییر tag به‌تنهایی اثبات استقرار نیست. rollback image به معنی rollback خودکار دیتابیس نیست.

تست‌های قبلی مرورگر با اجرای موازی روی Windows در دو تبِ background زمان‌سنجی ناپایدار داشتند. تست با آوردن تب هدف به foreground و حفظ assertionها اصلاح شد؛ مجموعهٔ اختصاصی دو تب 24/24 موفق شد. سپس بارکد عددی واقعی به تست اضافه و اجرای کامل سریالی آغاز شد. شکست‌های قبلی را پنهان نکن و برای Cloud نتیجهٔ CI روی head دقیق را ملاک قرار بده.

در Linux اولیه pg_dump 15 با سرور 16 ناسازگار بود و PHP mbstring نبود؛ محیط تست به PG16 و mbstring اصلاح شد، نه assertionها. تست‌های SIGTERM ویندوز را برای دورزدن تفاوت سیستم‌عامل تغییر ندادیم؛ مرجع کامل Linux موفق شد.

لاگ‌های Linux و شواهد استقرار در محیط خصوصی حفظ شده‌اند. نام و مسیرهای آن‌ها در فایل عملیاتی محلی آمده است. برای راستی‌آزمایی مستقل در Cloud، فرمان‌های همین سند را با دیتابیس disposable اجرا کن. محیط‌های تست قدیمی یا دیتابیس موجود را بازنشانی نکن.

## کارهای باز و ترتیب ادامه

1. PR و همهٔ CI jobها/review threadها را برای **آخرین SHA** بخوان. فقط در صورت موفقیت و رفع ایراد مادی merge کن. سبزبودن تست واحد جای ماتریس مرورگر یا بازبینی restore را نمی‌گیرد. تغییرات ذخیره‌شده در PR را از نو پیاده نکن.
2. ابتدا سرریز افقی reports/manager در عرض 375 را با دادهٔ واقعی رفع و regression کن؛ این مورد در جمع‌بندی 76 مسیر مشخص شد. نتیجهٔ نهایی مرورگر را بررسی/در Linux تکرار کن. پذیرش تعاملی صندوق در موبایل/دسکتاپ، اسکن سریع/دوربین/کیبورد، دو صندوق، قطع پاسخ، پیش‌نویس پرداخت‌دار و شیفت بسته، هر شش عرض، focus/zoom/کیبورد مجازی هنوز باید با شواهد تکمیل شود. UI پیام کمبود پس از اسکن و پیام کنار قلم را هم با معیار طرح تطبیق بده.
3. گزارش کاربران و اسنپ‌پی را در دادهٔ مشخص با دفتر/دریافت/مرجوعی تطبیق بده. مجوز invoice center برای نقش «فقط گزارش حسابداری» را بررسی کن؛ `requireInvoiceRead` ممکن است sale/return بخواهد. بدون تصمیم مستند دسترسی را باز نکن.
4. قبل از فعال‌کردن بکاپ: بازبینی مستقل امنیتی و race مصرف عامل دوم/کلید replay، audit ایجاد/دانلود، خطای تشخیصی خصوصی، نصب runtime و PG client، تنظیم امن root helper و هماهنگی compose با release فعال. سپس rehearsal قطع فرایند/rollback/قفل هم‌زمانی/نشست و حساب ممنوع در محیط جدا. هیچ یافتهٔ احتمالی این فهرست را بدون بازتولید، vulnerability تأییدشده اعلام نکن.
5. ادامهٔ یافته‌های امنیتی قدیمی؛ فهرست کامل شماره‌ها در [دفتر ۴۹ ردیف امنیتی](SECURITY-FINDINGS-HANDOFF-2026-09-26.md) حفظ شده است؛ شمارهٔ ردیف داخلی را با شمارهٔ لینک چت یا PR اشتباه نگیر. ردیف 49 از نظر موضوع تکرار 25 است. تنها رفع دارای شاهد را بسته اعلام کن. لینک‌های خصوصی/CSV اولیه در Cloud الزاماً قابل‌دسترسی نیستند؛ در صورت نیاز متن دقیق را از اتصال Codex Security/کاربر بگیر. ترتیب موارد شناخته‌شدهٔ باز:
   - FND29: قیود ارتباط سطر رسید با سفارش/شعبه/SKU/تأمین‌کننده؛ مرز را تقویت کن ولی receipt مشروع از سفارش پیشنهادی، انبار دیگر همان شعبه، اختلاف نرخ یا اضافه‌دریافت را بدون تصمیم مالی ممنوع نکن.
   - FND33/34: سازگاری migrationهای تاریخی 070 و 065؛ FND42: حالت legacy migration024/per_invoice. روی این سرور 82 checksum موجود تطبیق داشت؛ این به معنای حل همهٔ نصب‌های قدیمی نیست. راه ترمیم افزایشی و تست snapshot واقعی لازم است.
   - FND4: طبقه‌بندی مالیاتی/حساب هزینهٔ هدیه نیازمند تصمیم حسابدار؛ تأیید قبلی کاربر دربارهٔ مبلغ فاکتور جای تصمیم حساب مالیات نیست.

## اجرای مجدد قابل تکرار در Cloud

ابتدا `CLAUDE.md`، قواعد `.claude/`، ADRها، `docs/WEB-BACKUP-RESTORE.md` و این سند را بخوان. Node22+، pnpm10.33.0، PostgreSQL16 و ابزارهای client هم‌نسخه، PHP با mbstring لازم است. دیتابیس تست را کاملاً جدا بساز؛ فرمان db.sh test را هرگز با DATABASE_URL اصلی اجرا نکن. test helpers برای API به امکان ساخت DB آزمایشی نیاز دارند. متغیر `LMC_TEST_DB_ROLE=app` اجرای دوم با نقش محدود است، نه مجوز دادن به API زنده.

```sh
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
node --experimental-strip-types --test --test-concurrency=2 'apps/api/test/**/*.test.ts'
LMC_TEST_DB_ROLE=app node --experimental-strip-types --test --test-concurrency=2 'apps/api/test/**/*.test.ts'
bash ops/db.sh test
pnpm --filter @labelmod/web test
pnpm --filter @labelmod/web build
pnpm --filter @labelmod/web exec playwright install --with-deps chromium webkit
pnpm --filter @labelmod/web exec playwright test --workers=1
find integrations/woocommerce -name '*.php' -exec php -l {} \;
for t in payload-test push-receiver-test refund-test instore-test; do
  php "integrations/woocommerce/test/$t.php"
done
pnpm audit --prod --audit-level high
```

این فرمان‌ها بعد از آماده‌سازی env و DB تست‌اند؛ تنظیم DB/seed/نقش‌ها را از workflowهای `.github/workflows/` و helpers خود مخزن بگیر. Playwright config را قبل اجرا بخوان؛ preview/build باید تازه باشد. آرشیو/لاگ خصوصی PC را پیش‌نیاز Cloud نکن. اگر SSH یا secret در Cloud موجود نیست، کار کد و CI را ادامه بده و تست زندهٔ وابسته را «اجرانشده» بنویس، نه موفق.
