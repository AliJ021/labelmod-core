# اجرای سروری و تشخیص اتصال درگاه

این برش API پرداخت آنلاین را فعال نمی‌کند. آداپتور اسنپ‌پی با قرارداد آنلاین موجود
و انتقال HTTPS واقعی به اجرای سروری متصل شده، ولی تنها عملیات قابل فراخوانی از HTTP
تشخیص احراز است. موفقیت این آزمون یعنی credential در پاسخ همان احراز پذیرفته شد؛
به معنی پرداخت، تسویه، صحت callback، آمادگی تولید یا پشتیبانی صندوق و لینک پرداخت نیست.
دیجی‌پی تا دریافت قرارداد دقیق رسمی unsupported می‌ماند.

## پیکربندی مورد اعتماد

همه مقادیر فقط از محیط فرایند سرور خوانده می‌شوند؛ مسیر HTTP برای نوشتن آن‌ها وجود ندارد.
راز در platform.setting، audit، پاسخ آمادگی یا bundle مرورگر نمی‌رود. فعال‌سازی این تنظیم
یک کار استقرار مدیریت‌شده است؛ این تغییر هیچ محیطی را فعال یا اصلاح نکرده است.

| کلید محیطی | معنا |
|---|---|
| `SNAPPAY_API_MODE` | پیش‌فرض `disabled`؛ تنها مقدار قابل اجرا `diagnostic` است؛ `live` معتبر نیست |
| `SNAPPAY_API_BASE_URL` | HTTPS origin دقیق دریافتی از پذیرنده؛ بدون path/query/userinfo/hash؛ میزبان پیش‌فرض نداریم |
| `SNAPPAY_API_RETURN_URL` | نشانی HTTPS whitelist‌شدهٔ پذیرنده |
| `SNAPPAY_API_PAYMENT_ORIGINS` | آرایه JSON از originهای HTTPS تأییدشدهٔ صفحه پرداخت |
| `SNAPPAY_API_CLIENT_ID` / `SNAPPAY_API_CLIENT_SECRET` | اعتبارنامه OAuth، فقط سرور |
| `SNAPPAY_API_USERNAME` / `SNAPPAY_API_PASSWORD` | اعتبارنامه پذیرنده، فقط سرور |
| `SNAPPAY_API_TIMEOUT_MS` | ۱ تا ۳۰۰۰۰ میلی‌ثانیه؛ پیش‌فرض تشخیص ۱۰۰۰۰ |

تنظیم ناقص/نامعتبر، حالت `incomplete`/`invalid` می‌دهد و client شبکه فعال نمی‌شود.
خاموش‌بودن API، ثبت دستی فعلی اسنپ‌پی را عوض نمی‌کند. GET فقط نام کلیدهای مفقود را
می‌گوید، نه مقدار، میزبان یا credential. هیچ فراخوانی در startup یا GET انجام نمی‌شود.

## قرارداد HTTP داخلی

- `GET /payment-providers/readiness`: نشست انسانی کامل، مجوز `settings.view` و دامنه
  همه شعب لازم است. وضعیت ثبت دستی از حساب واسط و روش فعال فعلی خوانده می‌شود؛ وضعیت
  API جداست. `paymentIntegration` و `productionReady` همیشه false هستند.
- `POST /payment-providers/:provider/diagnose`: نشست انسانی کامل، `settings.security`،
  دامنه همه شعب و بدنه دقیق `{"confirmed":true}` لازم است. API key، PIN و بدنه حاوی
  نشانی یا credential رد می‌شوند. سقف ۳ درخواست در دقیقه دارد. فقط OAuth authenticate
  یک بار اجرا می‌شود؛ access token فوراً دور ریخته می‌شود. نه refresh، نه retry و نه
  فراخوانی token/verify/settle انجام می‌شود. نتیجه `authenticated` یا `unknown` است؛
  unknown ممکن است نشان‌دهنده دریافت درخواست در مقصد باشد. این تشخیص read-only محلی است:
  نه قصد پرداخت، نه رکورد وجه، نه تنظیم و نه لاگ بدنه می‌سازد؛ تضمین مالی once-only نمی‌دهد.

تشخیص دیجی‌پی unsupported است و هیچ شبکه‌ای ایجاد نمی‌کند. JSON خام درگاه، خطای شبکه،
access token، credential و نشانی tokenدار هیچ‌وقت در خروجی این مسیرها نیستند.

## انتقال HTTPS

هر درخواست فقط به origin پیکربندی‌شده می‌رود. DNS یک بار resolve می‌شود؛ اگر حتی یکی
از جواب‌ها خصوصی، loopback، link-local، رزروشده یا IPv4-mapped IPv6 باشد، اتصال رد می‌شود.
IP عمومی انتخاب‌شده در lookup همان اتصال پین می‌شود؛ hostname اصلی برای TLS حفظ می‌شود.
TLS حداقل ۱٫۳ و اعتبارسنجی گواهی اجباری است، agent مشترک/redirect/retry وجود ندارد.
Headerهای مجاز فقط Authorization و Content-Type هستند؛ encoding پاسخ identity است.
پاسخ بیش از ۲۵۶ KiB، encoding نامنتظره، HTTP ناموفق و redirect رد می‌شوند. درخواست
بیش از ۱ MiB رد می‌شود؛ سقف کل انتقال ۳۰ ثانیه و AbortSignal آداپتور هم مؤثر است.
این قیود ممکن است اتصال یک پذیرنده را نامعلوم کنند؛ هیچ fallback ناامن برای سبزکردن
تشخیص وجود ندارد و سازگاری TLS واقعی هنوز باید در stage سنجیده شود.

## مرز اجرایی ادغام مالی بعدی

قراردادهای زیر شرط پذیرش orchestration بعدی‌اند؛ زیرساخت آفلاین ۰۸۶ بخشی از آن‌ها را
طبق بخش پایانی پیاده می‌کند و هیچ اتصال مالی را فعال نمی‌کند:

1. جدول قصد تغییرناپذیر با UUID داخلی، provider/channel، invoice/branch، شناسه پذیرنده
   یکتای ۵–۱۰ رقم، hash بدنه کانونی، مبلغ ریالی، snapshot سبد سرور و revision پیکربندی.
   شناسه از DB تخصیص یابد؛ از UUID، زمان یا random کوتاه بریده نشود و پس از پایان بازه
   بازاستفاده نشود. برای همان idempotency key و بدنه متفاوت، ۴۰۹ الزامی است.
2. claim پیش از شبکه commit شود. انتقال حالت‌ها با compare-and-set نسخه و محدودیت
   یکتای `(intent,operation)` باشد؛ callback موازی فقط یک claim verify ایجاد کند.
   timeout/crash lease، ارسال تازه را مجاز نمی‌کند؛ worker claim را به unknown منتقل کند.
3. توکن و نتیجهٔ معتبر قبل از redirect پایدار شوند. توکن‌گیری نامعلوم بدون paymentToken
   فقط صف بررسی است؛ inquiry با transactionId در قرارداد موجود اثبات نشده است.
   هیچ retry/new intent خودکار برای دور زدن این حالت پذیرفته نیست.
4. callback تنها رویداد نامطمئن است؛ مبلغ و شناسه با snapshot تطبیق و event تکراری
   deduplicate شود. callback هرگز receipt نمی‌سازد. verify و settle intent/claim مستقل
   ولی مرتبط می‌خواهند؛ وضعیت verified هرگز settled تلقی نشود.
5. inquiry با paymentToken و snapshot ذخیره‌شده خوانده شود. نتیجه، مبلغ و transactionId
   باید همگی معتبر باشند. گذار unknown→verified/settled فقط از شاهد معتبر سرور مجاز است؛
   payload مرورگر یا انتخاب دستی status در این مسیر پذیرفته نیست.
6. رسید دریافت فقط برای شاهد settled معتبر، در تراکنش DB واحد همراه inbox/receipt link
   یکتا ساخته شود؛ همان `InvoiceService.addPaymentIn` و مسیر کانونی ثبت مالی استفاده شود.
   یکتایی provider/merchant transaction و intent→receipt مانع دو receipt برای همان وجه شود.
   crash پس از settle و پیش از commit با inquiry ادامه یابد؛ پس از commit همان receipt
   بازیابی شود. مبلغ ناخالص، credit یا سند واسط ساختگی برای دورزدن مسیر موجود ممنوع است.
7. cancel/refund نیازمند قصد مستقل و سقف وجه واقعی همان پرداخت اصلی است. بازپرداخت وب
   همچنان تأیید انسانی مستقل می‌خواهد؛ کلید API و callback نمی‌توانند آن را تأیید کنند.
8. آزمون الزامی: owner/restricted DB، دو callback/worker هم‌زمان، claim stale، قطع قبل/بعد
   از شبکه و commit، replay بدنه متفاوت، مبلغ بزرگ/شناسه غلط، rollback دفتر/موجودی، و
   عدم ثبت مالی برای تمام پاسخ‌های نامعلوم و verified بدون settle.

ذخیره قصد و ماشین حالت provider-independent را می‌توان با داده مصنوعی ساخت و آزمود؛
فعال‌سازی اتصال مالی به اسنپ‌پی همچنان به رفع ابهام شناسه پاسخ verify/settle، رفتار
توکن گمشده، قرارداد revert و آزمون stage نیاز دارد. این‌ها با auth diagnostic حل نمی‌شوند.
دیجی‌پی تا متن دقیق ticket/verify/deliver/refund/inquiry حتی قرارداد اجرایی مالی ندارد.

## شواهد و حدود

آزمون انتقال، DNS و credential همگی با پاسخ/سوکت تزریق‌شده محلی‌اند؛ هیچ تماس واقعی
با پذیرنده یا درگاه انجام نشده است. تست نقش HTTP روی PostgreSQL یک‌بارمصرف اجرا می‌شود.
UI جدیدی وجود ندارد؛ کار رابط برای مرحله جداگانه محفوظ است. تنها نقطه مشترک برنامه
افزودن ثبت route در `http/app.ts` است؛ تنظیمات پایگاه داده تغییر نکرده‌اند.

## زیرساخت آفلاین ۰۸۶

مهاجرت ۰۸۶ قصد و snapshot ریالی محاسبه‌شده از فاکتور/اقلام سرور را تغییرناپذیر ذخیره
می‌کند. مرجع داخلی ۵–۱۰ رقم از sequence بدون چرخش می‌آید؛ این مرجع قرارداد ticket
دیجی‌پی نیست. idempotency به کاربر و بدنه invoice/provider/configRevision متصل است.
برای هر فاکتور/provider فقط یک قصد مجاز است؛ پس عوض‌کردن کلید، قصد نامعلوم را دور نمی‌زند.
سیاست تلاش جدید پس از لغو هنوز تعریف نشده؛ محدودیت یک قصد در این برش عامدانه دائمی است.

رویدادها append-only هستند. قفل قصد و version، claimهای موازی را تک‌برنده می‌کنند.
مهلت ثابت ۳۰ ثانیه است؛ انقضا فقط unknown می‌سازد و worker یا retry خودکار ندارد.
بدون paymentToken، inquiry هم claim نمی‌شود. callback با مبلغ/مرجع دقیق و کلید dedupe
ذخیره می‌شود و هیچ حالت مالی را جلو نمی‌برد. شاهد معتبر داخلی با source، مبلغ و مرجع
تطبیق می‌شود؛ این marker اثبات رمزنگاری پاسخ درگاه نیست و فقط مرز trusted backend است.
توابع شاهد/claim نیازمند settings.security و شعبه مجازند؛ facade ساخت، نشست انسانی کامل
و sale.create می‌خواهد. مسیر HTTP این store وجود ندارد. نوشتن مستقیم نقش محدود حتی با
GRANT پیش‌فرض جدول‌های آینده رد می‌شود؛ UPDATE/DELETE برای مالک هم با trigger رد می‌شود.

settled_evidence تنها نام حالت شاهد ذخیره‌شده است؛ receipt، ledger، stock یا پرداخت
نمی‌سازد. پیش از وصل‌کردن شبکه باید snapshot جاری فاکتور مجدداً تطبیق/قفل شود، تفسیر
شناسهٔ پاسخ stage قطعی شود، claimهای HTTP به server adapter متصل شوند و receipt یکتای
کانونی در همان تراکنش inbox ساخته شود. snapshot ذخیره‌شده ثابت است ولی این برش خودِ
فاکتور را برای همیشه freeze نمی‌کند. هیچ‌کدام از این مرزها با وجود store، آمادهٔ تولید
یا پرداخت آنلاین تلقی نمی‌شوند.

مبلغ snapshot آفلاین ۰۸۶ جمع اقلام و حمل است، نه ماندهٔ قابل وصول: پرداخت‌های قبلی
و تخصیص تعویض ۰۸۵ از آن کم نمی‌شوند. پیش از فعال‌سازی مالی باید مبلغ جاری از مسیر
تسویهٔ مشترک، با احتساب پرداخت‌های قبلی و تخصیص/انتقال تعویض، زیر قفل دوباره محاسبه،
با قصد تطبیق و snapshot مربوط به دریافت وجه ثابت شود؛
از مبلغ ذخیره‌شدهٔ این store نباید مستقیماً رسید یا درخواست دریافت وجه ساخت.
