# مهاجرت داده از سیستم فعلی

انتقال کالاها، مشتریان، تأمین‌کنندگان، موجودی اول دوره و مانده‌های
افتتاحیه به لیبل مد.

> **این کار یک بار انجام می‌شود و برگرداندنش سخت است.** پس ابزار
> پیش‌فرضش **آزمایشی** است: بدون `--commit` هیچ‌چیز نوشته نمی‌شود.

---

## ۰. آنچه منتقل می‌شود — و آنچه نمی‌شود

**می‌شود**

| فایل | چه چیزی |
|---|---|
| `products.csv` | کالا و تنوع‌ها با SKU، رنگ، سایز، بارکد، قیمت |
| `customers.csv` | مشتری با موبایل و حد اعتبار |
| `suppliers.csv` | تأمین‌کننده |
| `opening-stock.csv` | موجودی اول دوره **با بهای تمام‌شده** |
| `opening-balances.csv` | نقد، بانک، دریافتنی، پرداختنی |

**نمی‌شود، و عمداً**

- **تاریخچه فاکتورهای قبلی.** آن‌ها در سیستم قبلی می‌مانند و باید
  بمانند: سند حسابداریِ ساخته‌شده در یک سیستم دیگر، وقتی به این دفتر
  بیاید، نه قابل حسابرسی است و نه قابل اعتماد. اگر فردا کسی بپرسد
  «این عدد از کجا آمد»، جوابی نیست.
- **گردش حساب و اسناد قدیمی.** به‌جایش **مانده** می‌آید — که همان
  چیزی است که یک سند افتتاحیه معنا دارد.
- **سود و زیان دوره‌های قبل.** آن مال سیستم قبلی است.

سیستم قبلی را **نگه دارید و بایگانی کنید**. مهاجرت یعنی «از اینجا به
بعد»، نه «انگار همیشه اینجا بوده».

---

## ۱. خروجی گرفتن از سیستم فعلی

از نرم‌افزار فعلی خروجی اکسل بگیرید و در اکسل ستون‌ها را به شکل زیر
مرتب کنید. **نام ستون‌ها باید دقیقاً همین‌ها باشند** (بزرگی و کوچکی
حروف مهم نیست).

نمونه‌های آماده در `docs/import-samples/` هستند — همان‌ها را باز کنید و
داده خودتان را جایشان بگذارید.

### ذخیره‌کردن در اکسل

**File ← Save As ← CSV UTF-8 (Comma delimited)**

⚠️ حتماً **UTF-8**. `CSV (Comma delimited)` ساده، فارسی را خراب
می‌کند و نام کالاها به علامت سؤال تبدیل می‌شوند.

اگر اکسل شما به‌جای کاما نقطه‌ویرگول می‌نویسد، مشکلی نیست — ابزار
خودش تشخیص می‌دهد.

**رقم فارسی مشکلی ندارد.** «۱٬۵۰۰٬۰۰۰» درست خوانده می‌شود.

## ۲. قرارداد فایل‌ها

### `products.csv`

| ستون | اجباری | توضیح |
|---|---|---|
| `sku` | ✅ | **کلید مهاجرت.** یکتا در کل فایل |
| `name` | ✅ | نام کالا |
| `color` | | رنگ |
| `size` | | سایز |
| `barcode` | | بارکد کارخانه، اگر هست |
| `price` | | قیمت فروش به **ریال** |
| `legacy_id` | | کد کالا در سیستم قبلی — برای رهگیری |

⚠️ **SKU کلید است، نه بارکد.** بارکد ممکن است نباشد، تکراری باشد یا
عوض شود. SKU چیزی است که انباردار روی برچسب می‌بیند.

هر ترکیب رنگ و سایز یک سطر است: پیراهن سفید L و پیراهن سفید XL دو
سطر با دو SKU جدا.

### `opening-stock.csv`

| ستون | اجباری | توضیح |
|---|---|---|
| `sku` | ✅ | باید در `products.csv` باشد |
| `qty` | ✅ | تعداد. تا سه رقم اعشار |
| `unit_cost` | ✅ | **بهای تمام‌شده هر واحد**، به ریال |

⚠️ **`unit_cost` اجباری است و این مذاکره‌پذیر نیست.**

موجودی بدون بها یعنی اولین فروشِ آن کالا سودِ صددرصد نشان می‌دهد، و
ترازنامه دارایی‌ای دارد که ارزشش صفر است. اگر بهای واقعی معلوم نیست،
مهاجرت باید بایستد تا کسی تصمیم بگیرد — نه اینکه صفر فرض شود.

بهای تمام‌شده یعنی **قیمت خرید**، نه قیمت فروش.

کالای با تعداد صفر رد می‌شود و هشدار می‌گیرد.

### `customers.csv`

| ستون | اجباری | توضیح |
|---|---|---|
| `mobile` | ✅ | کلید تطبیق. «۰۹۱۲…»، «+98912…» و «0912…» یکی‌اند |
| `name` | | نام کامل |
| `credit_limit` | | سقف نسیه به ریال. خالی یعنی صفر |
| `legacy_id` | | کد مشتری در سیستم قبلی |

مشتری بدون موبایل وارد نمی‌شود: موبایل تنها کلیدی است که همان مشتری را
از صندوق و از سایت یکی می‌کند.

### `suppliers.csv`

| ستون | اجباری | توضیح |
|---|---|---|
| `code` | ✅ | کد تأمین‌کننده. یکتا |
| `name` | ✅ | نام |
| `mobile` | | |
| `legacy_id` | | |

### `opening-balances.csv`

| ستون | اجباری | توضیح |
|---|---|---|
| `leg` | ✅ | یکی از `cash` · `bank` · `receivable` · `payable` |
| `amount` | ✅ | مبلغ **مثبت** به ریال |
| `party` | برای دریافتنی و پرداختنی | موبایل مشتری یا کد تأمین‌کننده |
| `note` | | شرح |

⚠️ **مبلغ همیشه مثبت است.** جهت (بدهکار یا بستانکار) از `leg` می‌آید،
نه از علامت عدد.

⚠️ **`inventory` و `equity` در این فایل نیستند و نباید باشند:**

- **موجودی کالا** از جمع `opening-stock.csv` ساخته می‌شود. اگر دستی
  هم نوشته می‌شد، دو عدد داشتیم که باید همیشه با هم بخوانند — و روزی
  نمی‌خوانند.
- **سرمایه** رقم **متوازن‌کننده** است: دارایی منهای بدهی. سرمایه‌ای
  که دستی نوشته شود و سند را متوازن نکند، فقط یک خطای دیرهنگام
  می‌سازد.

هر مشتری بدهکار یک سطر `receivable` می‌گیرد و هر تأمین‌کننده بستانکار
یک سطر `payable`. **بدون `party` ثبت نمی‌شوند** — گردش حساب اشخاص از
دفتر ساختنی نیست اگر سطر سند نداند مال کیست.

## ۳. اجرای آزمایشی

فایل‌ها را در یک پوشه بگذارید (مثلاً `./migration`) و:

```bash
node --experimental-strip-types apps/api/src/cli/import-legacy.ts \
  --dir ./migration --branch MAIN --warehouse STORE
```

روی سرور، داخل ظرف:

```bash
docker compose -f docker-compose.prod.yml run --rm -v "$PWD/migration:/migration:ro" api \
  node --experimental-strip-types apps/api/src/cli/import-legacy.ts \
  --dir /migration --branch MAIN --warehouse STORE
```

خروجی یا فهرست خطاها را می‌دهد، یا این گزارش (اعداد از فایل‌های
نمونه `docs/import-samples/`):

```
── اجرای آزمایشی ──────────────────────────

  کالا           ۴ تازه، ۰ از قبل موجود
  مشتری          ۳ تازه، ۰ از قبل موجود
  تأمین‌کننده     ۲ تازه، ۰ از قبل موجود
  موجودی         ۴ سطر

  ── سند افتتاحیه (تومان) ──
  موجودی کالا             ۲٬۷۴۰٬۰۰۰
  نقد                     ۱٬۲۰۰٬۰۰۰
  بانک                    ۸٬۵۰۰٬۰۰۰
  دریافتنی                  ۳۰۰٬۰۰۰
  پرداختنی                ۲٬۰۰۰٬۰۰۰  (بستانکار)
  ─────────────────────────────────────────
  سرمایه                 ۱۰٬۷۴۰٬۰۰۰  ← رقم متوازن‌کننده
```

### خطاها

هر خطا فایل، شماره سطر و ستون را می‌گوید:

```
opening-stock.csv:47 [sku] SKU «P-9999» در فایل کالاها نیست
products.csv:12 [sku] SKU تکراری: P-1001
opening-balances.csv:5 [party] مشتری با موبایل «09190000000» در فایل مشتریان نیست
```

**همه خطاها یک‌جا می‌آیند، نه اولی.** یک بار اصلاح کنید، نه هزار بار.

## ۴. ⚠️ تأیید سرمایه — پیش از `--commit`

عدد **سرمایه** را به حسابدار نشان دهید.

این رقم را کسی وارد نکرده؛ محاسبه شده است:

```
سرمایه = موجودی کالا + نقد + بانک + دریافتنی − پرداختنی
```

اگر با آنچه حسابدار انتظار دارد نمی‌خواند، یعنی یکی از ورودی‌ها غلط
است — نه اینکه سرمایه غلط باشد. معمولاً:

- بهای تمام‌شده موجودی با قیمت فروش اشتباه گرفته شده
- مانده بانکی از صورت‌حساب گرفته شده، نه از دفتر
- بدهی تأمین‌کننده‌ای جا افتاده

عددی که بی‌آنکه کسی ببیند در دفتر بنشیند، ماه‌ها بعد در ترازنامه پیدا
می‌شود.

## ۵. اجرای واقعی

```bash
node --experimental-strip-types apps/api/src/cli/import-legacy.ts \
  --dir ./migration --branch MAIN --warehouse STORE --commit
```

همه‌چیز در **یک تراکنش** نوشته می‌شود: یا همه، یا هیچ.

### پس از اجرا

```sql
-- باید خالی باشد: Projection موجودی با حرکت‌ها می‌خواند
SELECT * FROM inventory.balance_check WHERE qty_diff <> 0 OR value_diff <> 0;

-- باید خالی باشد
SELECT * FROM sales.unposted_revenue;

-- سند افتتاحیه
SELECT account_code, sum(debit), sum(credit)
  FROM ledger.journal_line l
  JOIN ledger.journal_entry e ON e.id = l.entry_id
 WHERE e.kind = 'opening'
 GROUP BY account_code ORDER BY account_code;

-- گردش حساب اشخاص
SELECT * FROM ledger.party_tafsili;
```

## ۶. اجرای دوباره — امن است

اگر مطمئن نیستید اجرا موفق بوده، **دوباره اجرا کنید**. سه محافظ:

- کالای موجود دوباره ساخته نمی‌شود، و **به‌روز هم نمی‌شود** — نامی که
  کسی در سیستم اصلاح کرده، به مقدار فایل قدیمی برنمی‌گردد.
- موجودی افتتاحیه‌ای که یک بار ثبت شده، دوباره ثبت نمی‌شود. **موجودی
  دو برابر نمی‌شود.**
- سند افتتاحیه دوم، اولی را معکوس می‌کند و جایش می‌نشیند — نه اینکه
  رویش جمع شود (`ledger.post_opening_balance`).

## آنچه بعد از مهاجرت باید دستی انجام شود

| کار | چرا |
|---|---|
| تعریف کاربران پرسنل | `ops/deploy.sh user` — رمزشان تصادفی است و یک بار چاپ می‌شود |
| تنظیم شرایط تسویه پایانه‌ها | از PSP بگیرید؛ در `treasury.account` می‌نشیند |
| تأیید کدینگ حساب و روش قیمت تمام‌شده | صفحه تنظیمات — پیش از اظهارنامه |
| چک‌های در جریان | با `treasury.post_cheque_event` وارد شوند، نه مانده افتتاحیه |

⚠️ **چک‌های در جریان در فایل مانده‌ها نیستند.** چک یک سند مستقل است
(ADR-004) و وضعیتش از زنجیره رویداد می‌آید. چکی که به‌عنوان «دریافتنی»
وارد شود، در پرونده چک نیست و سررسیدش هشدار نمی‌گیرد.
