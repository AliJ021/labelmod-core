# تشخیص اتصال ووکامرس — نسخهٔ ۱٫۲٫۰

مبنا: `047a65e2efa91afba36843f73356492aa06e12ba`. این تغییر مهاجرت یا تغییر هستهٔ مالی ندارد.

## قرارداد و دسترسی

- `GET /web/connection`: احراز هویت موجود + `sale.create`، سپس دامنهٔ شعبه و انبار؛
  ورودی UUIDها و SKU/variationId اختیاری. فقط وجود SKU فعال و انطباق آن با شناسه را می‌خواند.
- `GET /settings/woocommerce`: `settings.view`؛ تنظیمات عمومی و فقط وجود کلید امضا در API.
- `POST /settings/woocommerce/test`: `settings.view` + دامنهٔ انبار تنظیم‌شده، CSRF نشست و
  سقف ۶ درخواست در دقیقه؛ هیچ مقصدی از بدنه پذیرفته نمی‌شود. فقط تنظیم `web.site_url`.
- `POST /wp-json/lmc/v1/diagnostics`: همان نگهبان HMAC/timestamp/nonce تولیدی Push.
  فقط گزارش نسخهٔ نصب‌شده، هویت سایت، پیکربندی، شمارش نگاشت و وضعیت محدود سفارش انتخابی.
  هیچ مشتری، مبلغ، کلید یا متن خام خطا در پاسخ نیست. ثبت nonce تنها نوشتن امنیتی این مسیر است.
- سمت Core همان `resolveSafeTarget` و `pinnedLookup` موجود استفاده می‌شوند؛ همهٔ پاسخ‌های
  DNS سنجیده و به اتصال پین می‌شوند. HTTPS، بدون redirect، حداکثر پاسخ ۳۲KiB و timeout شبکه ۸ ثانیه.
- کلاینت افزونه از `wp_safe_remote_request` وردپرس با HTTPS و `redirection=0` استفاده می‌کند؛
  محدودیت‌های اعتبارسنجی HTTP وردپرس برقرارند. متن خام خطای شبکه یا مقصد در تشخیص بازتاب نمی‌شود.

خواندن موفق کلید API از داخل وردپرس با تأیید HMAC از Core دو شاهد جدا هستند. وجود کلید،
زمان‌بندی رویداد یا متای فاکتور، اجرای موفق Worker/cron و صحت موجودی را اثبات نمی‌کند.
نسخهٔ استقرار Core از این پروتکل قابل استنتاج نیست؛ `protocol=1` نسخهٔ قرارداد است.

## شواهد علت‌های محتمل گزارش TEST

`LMC_Order_Sync::payment_complete` تنها Hook ارسال خودکار سفارش است. `is_eligible` علامت
`_lmc_payment_complete=yes` و وضعیت مجاز را لازم می‌داند. پس تغییر دستی status به processing
به‌تنهایی ارسال نمی‌سازد؛ این رفتار، دفاع موجود در برابر ثبت پرداخت‌نشده است و تغییر نکرده است.

`LMC_Order_Sync::build_payload` فقط SKU می‌فرستد و نبودش را رد می‌کند.
`WebOrderService.resolveSku` فقط SKU فعلی فعال را در Core می‌پذیرد. اما دریافت موجودی و قیمت
از `_lmc_variation_id` استفاده می‌کند. بنابراین توضیح قدیمی «پس از نگاشت SKU آزاد است» دربارهٔ
سفارش درست نبود. متن راهنما اصلاح شد؛ قرارداد سفارش تغییر نکرد.

برای توسعهٔ بعدی، پیشنهاد محدود این است که `variationId` اختیاری در سفارش پذیرفته شود و با
شناسهٔ فعال و نگاشت مجاز سمت سرور حل شود؛ SKU برای سفارش‌های قدیمی fallback بماند. باید سیاست
تعارض SKU/شناسه، اتصال سایت، snapshot پیش از نخستین تلاش و payload کلید idempotency برای replay
قدیمی صریح حفظ شوند. این پیشنهاد **پیاده نشده** و مالکیت shared core با جریان B است.

هیچ‌یک از علت‌های بالا علت قطعی سفارش گزارش‌شده نیست. دسترسی زندهٔ TEST و آزمون کنترل‌شده
انجام نشده‌اند. معیار پذیرش TEST: موجودی قبل/بعد روی یک تنوع، یک سفارش پرداخت‌شده، یک فاکتور،
یک خروج انبار، سپس duplicate/response-loss retry با همان externalId بدون خروج دوم؛ Push مطلق
و خارج‌ازترتیب، و وضعیت/خطای cron هم ثبت شوند. هیچ اثر مالی آزمایشی بدون مجوز زنده اجرا نشود.

## پوشش بررسی

- آزمون قرارداد Node: امضا، nonce تازه در تکرار، مقصد خصوصی/mixed DNS، HTTPS، redirect، پاسخ
  نامعتبر، هویت سایت، حذف فیلدهای اضافه، خطای بدون راز، پین واقعی اتصال و قطع پاسخ بزرگ.
- آزمون PHP: تشخیص تکراری بدون ذخیرهٔ سفارش، paid/status، SKU/نگاشت مفقود، cron، خطای بدون راز،
  استفاده از نگهبان موجود، روش GET و جلوگیری از redirect در کلاینت.
- آزمون API یکپارچه در پروندهٔ سفارش موجود: کلید باطل/ناموجود، دامنه، mapping mismatch،
  دو خواندن بدون تغییر شمار فاکتور/حرکت/inbox و منع دسترسی نقش سایت به تنظیمات.
- بسته: دو ساخت بایت‌به‌بایت یکسان، تطبیق نسخه/نام/اندازه/SHA256 و وجود فایل تشخیص در ZIP.
- رگرسیون‌های موجود سفارش، refund، Push و دریافت حضوری باید بدون کاهش پوشش اجرا شوند.
