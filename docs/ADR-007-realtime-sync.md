# ADR-007 — همگام‌سازی لحظه‌ای موجودی و قیمت با سایت

**وضعیت:** پذیرفته‌شده · **کد ساخته شد** (مهاجرت ۰۵۷) — با یک شرط
پذیرشِ **باز** که در بخش «مانع» مانده است
**تاریخ:** شهریور ۱۴۰۵ · **تصمیم‌گیرنده:** مالک محصول

## زمینه

امروز افزونه با WP-Cron و بازهٔ `lmc_quarter_hour` هر **۱۵ دقیقه** خوراک
موجودی را از Core **می‌کشد (Pull)**. پیامدش یک عدد است، نه یک حس:

> پس از فروش آخرین قلم در فروشگاه، سایت تا **۱۵ دقیقه** همان کالا را
> موجود نشان می‌دهد و می‌فروشد.

پنجرهٔ فروشِ‌اضافی (Oversell) پانزده دقیقه است. مالک تصمیم گرفته این به
**ارسال لحظه‌ای (Push)** تبدیل شود تا آن پنجره به چند ثانیه برسد.

## تصمیم

**Push از Core به سایت، با الگوی Transactional Outbox.** و نه با HTTP
همگام.

### چرا نه HTTP همگام داخل تراکنش فروش

سه دلیل، هر سه از قواعد موجود همین مخزن:

۱. **بودجهٔ ۱۰۰ms صندوق** (ADR-002). اندازه‌گیری بخش ۸٫۸ ممیزی نشان داد
   سهم سرور امروز ~۱۱ms است و کل زمان محسوس ۵۶–۸۷ms. یک درخواست HTTP به
   سایت، حتی موفق، این بودجه را می‌شکند.
۲. **قطعی سایت نباید فروش حضوری را متوقف کند.** فروشگاه باید بفروشد حتی
   اگر سایت پایین باشد.
۳. **اثر جانبی ناموفق نباید فروشِ Commit‌شده را نامعتبر کند** (بند ۲۲
   الحاقیه) — همان قاعده‌ای که برای پیامک هم برقرار است.

### زیرساخت تازه‌ای لازم نیست

این یک ماژول بزرگ نیست. آنچه از قبل هست:

```
platform.outbox_message        جدول صف
platform.claim_outbox()        اجاره، نه قفل — Worker مرده دوباره برداشته می‌شود
platform.complete_outbox()     پایان موفق
platform.fail_outbox()         Backoff، و نامهٔ مرده پس از سقف تلاش
platform.outbox_dead           نمای شکست دائم
apps/api/src/worker/loop.ts    چرخهٔ Worker
apps/api/src/worker/webhook.ts فرستندهٔ Webhook
```

آنچه اضافه می‌شود: یک `topic` تازه، درج سطر در **همان تراکنش** حرکت
انبار، و یک مسیر REST گیرنده در افزونه.

## یادداشت طراحی

### ۱. نام `topic` و شکل Payload

```
topic: 'web.stock_push'        موجودی یک تنوع
topic: 'web.price_push'        قیمت یک تنوع
```

```jsonc
{
  "variationId": "01a0…",        // کلید اتصال — همان چیزی که افزونه در
                                 // _lmc_variation_id نگه می‌دارد
  "sku":         "SKU-1234",     // فقط برای اتصال اولیه و لاگ، نه تطبیق
  "onHand":      7,              // **مقدار مطلق**، نه تفاضل
  "priceRial":   "1850000",      // رشته — پول در JSON هرگز number نیست
                                 // null یعنی «قیمت ندارد»، نه مجانی
  "version":     84213,          // شمارندهٔ صعودی — نگهبان ترتیب
  "at":          "2026-09-13T…"  // فقط برای انسان؛ تصمیم با version است
}
```

⚠️ **مقدار مطلق، نه تفاضل — مهم‌ترین قید این طراحی.** `CLAUDE.md` صریح
است که تحویل Outbox **«حداقل یک بار» است، نه «دقیقاً یک بار»**. با
«−۱»، یک تحویل تکراری یا گم‌شده موجودی سایت را **برای همیشه** خراب
می‌کند. با «الان ۷ است»، تکرار بی‌ضرر است و گم‌شدن هم با پیام بعدی یا
تور ایمنی جبران می‌شود.

### ۲. کجا سطر Outbox درج می‌شود

**داخل `inventory.apply_movement()`** — و این انتخاب دلیل دارد، نه
سلیقه: `CLAUDE.md` می‌گوید «موجودی فقط از `apply_movement()` تغییر
می‌کند». پس هر مسیری که موجودی را عوض می‌کند خودبه‌خود پوشش می‌گیرد و
**هیچ‌کدام جا نمی‌ماند**:

```
فروش · مرجوعی · رسید خرید · برگشت از خرید · انتقال بین انبارها ·
انبارگردانی · تجدید ارزیابی · بایگانی کالا
```

⚠️ **تجدید ارزیابی تعداد را عوض نمی‌کند** (حرکت با تعداد صفر)، پس فقط
وقتی پیام می‌سازد که قیمت **فروش** عوض شده باشد — که مسیرش
`catalog.set_price()` است، نه `apply_movement`.

قیمت: **داخل `catalog.set_price()`**، به همان دلیل — تنها مسیر مجاز
تغییر قیمت است.

⚠️ `apply_movement` از مهاجرت ۰۵۰ `SECURITY DEFINER` با `search_path`
پین‌شده است و `platform` در آن مسیر هست، پس درج در `outbox_message` از
داخلش بی اشکال است. سنجیده شد، فرض نشد.

⚠️ و یک نکتهٔ انبار: پیام باید **جمع همهٔ انبارهای قابل فروش سایت** را
ببرد، نه `on_hand` همان انباری که حرکت در آن افتاد. انتقال بین دو انبارِ
همان شعبه جمع را عوض نمی‌کند، پس نباید پیامِ «موجودی عوض شد» بسازد —
وگرنه هر انتقال داخلی، سایت را بی‌دلیل به‌روز می‌کند.

### ۳. تجمیع (Coalescing)

۵۰ قلم در یک دقیقه نباید ۵۰ درخواست بسازد. `outbox_message` امروز کلید
یکتایی به‌ازای موجودیت **ندارد** — تنها ایندکسش
`(next_attempt_at, id) WHERE status IN ('pending','sending')` است.

پس تجمیع لازم می‌آورد:

```sql
-- ایندکس یکتای جزئی: برای هر (topic, variation) حداکثر یک سطر معلق
CREATE UNIQUE INDEX outbox_pending_entity_idx
  ON platform.outbox_message ((payload->>'variationId'), topic)
  WHERE status = 'pending';
```

و درج به‌شکل `INSERT … ON CONFLICT … DO UPDATE SET payload = EXCLUDED.payload`
— یعنی سطر معلق با **آخرین** وضعیت بازنویسی می‌شود. چون Payload مقدار
مطلق دارد، بازنویسی بی‌خطر است.

⚠️ شرط `status = 'pending'` اجباری است: سطری که `sending` شده در حال
رفتن است و نباید Payloadش زیر پای فرستنده عوض شود. آن حالت پیام
**بعدی** می‌سازد.

⚠️ Backpressure: اگر صف عقب بیفتد، رفتار **تعریف‌شده** همین تجمیع است —
صف حداکثر به اندازهٔ «تعداد تنوع‌های تغییرکرده» رشد می‌کند، نه به اندازهٔ
«تعداد حرکت‌ها». سقف انفجار ساختاری بسته است، نه با یک عدد.

### ۴. نسخه‌گذاری و نگهبان ترتیب

`version` = `stock_movement.id` (شمارندهٔ صعودی و تکرارنشدنی دیتابیس).
برای قیمت = `catalog.price.id` سطر تازه.

افزونه آن را در متای `_lmc_stock_version` (و `_lmc_price_version`)
نگه می‌دارد و **پیام با نسخهٔ مساوی یا قدیمی‌تر را دور می‌اندازد**.

⚠️ بی این نگهبان، دو فروش پشت سر هم = دو پیام، و اگر پیام اول دیرتر
برسد سایت عدد کهنه را می‌نشاند. بندهای ۱۵ و ۱۶ الحاقیه.

⚠️ مقایسه باید `>=` باشد نه `>`: تحویل تکراریِ **همان** پیام هم باید
دور انداخته شود، وگرنه یک Retry بی‌دلیل `post_meta` را می‌نویسد.

### ۵. مسیر REST افزونه و امضا

```
POST /wp-json/lmc/v1/stock      Body: JSON بالا
POST /wp-json/lmc/v1/price
```

امضا: **HMAC-SHA256 روی Body خام** + Timestamp + Nonce.

```
X-LMC-Timestamp: 1789311045          ± ۳۰۰ ثانیه، وگرنه رد
X-LMC-Nonce:     <۱۶ بایت تصادفی>    در یک Transient وردپرس نگه می‌شود
X-LMC-Signature: sha256=<hex>        HMAC(secret, timestamp + "." + nonce + "." + body)
```

⚠️ روی **Body خام** امضا می‌شود نه روی JSON بازتولیدشده: هر
Serialize دوباره می‌تواند ترتیب کلید یا فاصله را عوض کند و امضا را
بی‌دلیل بشکند.

⚠️ Nonce بی Timestamp کافی نیست (حافظهٔ Nonce باید بی‌نهایت باشد) و
Timestamp بی Nonce هم کافی نیست (پنجرهٔ ۳۰۰ ثانیه‌ای Replay). **هر دو.**

⚠️ **راز در متغیر محیطی، نه در `platform.setting`** — همان قاعده‌ای که
`SMS_API_KEY` دارد: مقدار هر تنظیم در `audit_log` می‌نشیند و صفحهٔ
تنظیمات نشانش می‌دهد. راز نباید هیچ‌کدام را ببیند.
سمت افزونه: در `wp-config.php` به‌عنوان ثابت، نه در `wp_options`.

⚠️ مقایسهٔ امضا با `hash_equals()` سمت PHP و `timingSafeEqual` سمت Node.

### ۶. SSRF روی نشانی مقصد

نشانی سایت یک **ورودی پیکربندی** است، پس یک سطح حمله است (بند ۶۲
الحاقیه). پیش از هر درخواست:

```
طرح باید https باشد
IP مقصد پس از DNS نباید در این محدوده‌ها باشد:
  127.0.0.0/8 · 10/8 · 172.16/12 · 192.168/16 · 169.254/16 · ::1 · fc00::/7
Redirect **دنبال نمی‌شود** (redirect: 'manual') — وگرنه یک Redirect
  به 169.254.169.254 همهٔ سنجش‌های بالا را دور می‌زند
Timeout مشخص و سقف تلاش، تا سایت کند Worker را قفل نکند
```

⚠️ سنجش نشانی پیش از DNS کافی نیست: نامی که به IP داخلی Resolve شود از
هر بررسی رشته‌ای رد می‌شود. سنجش باید روی **IP نهایی** باشد.

### ۷. چرخهٔ ۱۵ دقیقه‌ای **حذف نمی‌شود** — نقشش عوض می‌شود

از «مکانیزم اصلی» به **«تور ایمنی تطبیق»**. دلیلش این است که Push
می‌تواند شکست بخورد (سایت پایین، افزونه غیرفعال، نامهٔ مرده) و کسی هم
ممکن است مستقیم در پیشخان سایت موجودی را دست بزند. فقط یک تطبیق دوره‌ای
واگرایی را کشف می‌کند.

⚠️ آن اجرا **اختلاف را گزارش می‌کند، نه بی‌صدا درست می‌کند.** تصحیح
خودکارِ بی‌صدا یعنی علت هرگز پیدا نشود.

⚠️ بازه‌اش یک **تنظیم** می‌شود (`web.reconcile_minutes`)، نه عدد ثابت در
کد.

### ۸. جهت معکوس: **ساخته نمی‌شود**

مالک گفته «و برعکس در همه بخش‌ها». این یک خطر واقعی دارد و عمداً انجام
نمی‌شود:

- **موجودی و قیمت: مرجع نهایی فقط Core است. یک‌طرفه، Core → سایت.**
  اگر سایت هم بتواند در Core بنویسد، حلقهٔ Ping-pong و Stale Overwrite
  بند ۱۶ الحاقیه ساخته می‌شود و دیگر معلوم نیست عدد درست کجاست.
- آنچه واقعاً باید سایت → Core بیاید **سفارش** است، و از قبل کار
  می‌کند: `POST /web/orders` با `Idempotency-Key` ساخته‌شده از **شماره
  سفارش ووکامرس**، نه از هدر کلاینت.
- اگر مالک نوشتن موجودی از سمت سایت را بخواهد، آن یک **تصمیم تازه** است
  و ADR جداگانه می‌خواهد.

### ۹. صفر و null

قیود موجود `CLAUDE.md` سر جایشان می‌مانند و با Push **پرتکرارتر** و
حساس‌تر می‌شوند:

```
onHand = 0        → ناموجود؛ manage_stock و stock_status هم‌زمان و سازگار
priceRial = null  → «قیمت ندارد»، **نه مجانی**. نوشتن صفر یعنی ویترین
                    کالا را رایگان بفروشد
backorders        → اجباراً 'no' وقتی موجودی از Core مدیریت می‌شود
```

PR #51 همین رفتار صفر را تازه اصلاح کرده؛ Push آن اصلاح را از «گاهی» به
«همیشه» می‌برد.

### سه انحراف از همین سند، و دلیلشان

**۱. «جمع همهٔ انبارهای قابل فروش سایت» → یک انبار.** بند ۲ این را
خواسته بود. چنین مفهومی در اسکیما **وجود ندارد**: نه ستون
`web_sellable`ی هست و نه خوراک فعلی چندانباره است — `/web/stock` یک
`warehouseId` می‌گیرد و افزونه یکی را پیکربندی می‌کند. ساختن مفهوم تازه
فقط برای Push یعنی **دو تعریف از «موجودی سایت»**، و آن‌وقت تور ایمنیِ
بند ۷ هر بار یک واگرایی **کاذب** گزارش می‌کند و خیلی زود کسی دیگر
نگاهش نمی‌کند. پس همان فرمول خوراک: `on_hand − reserved` روی همان انبار،
از تنظیم `web.stock_warehouse`.

⚠️ نتیجهٔ جانبی و **درست**: انتقال میان دو انبار غیرسایتی هیچ پیامی
نمی‌سازد (بند ۲ همین را می‌خواست)، و انتقال از انبار سایت به انبار دیگر
**می‌سازد** — چون واقعاً از ویترین کم کرده است.

**۲. `version` = شناسهٔ سطر → یک دنباله.** بند ۴ نوشته بود
«`stock_movement.id` (شمارندهٔ صعودی و تکرارنشدنی دیتابیس)». این دربارهٔ
اسکیمای این مخزن **غلط** است: آن ستون و `catalog.price.id` هر دو `uuid`
هستند. پس `platform.web_push_version`، یک `SEQUENCE` واقعی. `nextval`
غیرتراکنشی است — حتی اگر فروش Rollback شود عدد مصرف می‌شود و هرگز تکرار
نمی‌گردد، که برای شمارندهٔ نسخه دقیقاً همان لازم است.

⚠️ و چرا ساعت به‌کار نمی‌آمد: `occurred_at` از بیرون قابل تعیین است، پس
یک حرکتِ عقب‌تاریخ نسخه‌ای کوچک‌تر می‌ساخت و پیام درست را دور می‌انداخت.

**۳. تجدید ارزیابی.** بند ۲ می‌گفت پیام نمی‌سازد. درست است ولی نه به آن
دلیل: `apply_movement` **حرکت با تعداد صفر را اصلاً نمی‌پذیرد**، پس
مسئله منتفی است. یک بند تست همین را ثبت کرده.

### و یک باگ که همین کار پیدایش کرد

حلقهٔ Worker وقتی `notify.sms_enabled` خاموش بود، **هر** پیامی را
بی‌صدا `sent` می‌کرد — با این استدلال که «خاموش‌بودن پیامک یک شکست
نیست». درست بود وقتی تنها کانال، پیامک بود. ولی از وقتی `health.alert`
هم Webhook می‌فرستد، یعنی:

    notify.sms_enabled = false  +  notify.webhook_enabled = true
    → هشدار سلامت بی‌صدا بسته می‌شد و هیچ Webhookی نمی‌رفت

همان کلاس FND-021: کلیدی که روشن است و هیچ کاری نمی‌کند. Push سایت هم از
همین‌جا رد می‌شد. حالا آن میان‌بر فقط برای `SMS_ONLY_TOPICS` است و
`handleHealthAlert` خودش خاموشیِ پیامک را می‌سنجد.

## مانع — و شرط پذیرشی که هنوز باز است

بخش ۸٫۹ پرامپت صریح می‌گوید محیط WooCommerce واقعی «برای بخش ۸٫۱۳ هم
لازم است». آن محیط در این ممیزی **در دسترس نبود**، و این آزموده شد نه
فرض:

```
دانلود WordPress و WooCommerce    → 000 / 403 از Proxy
git clone هر دو                   → موفق، ولی WooCommerce یک Monorepo
                                     است و Build خودش را می‌خواهد
apt-get install mariadb-server    → 404 و 403؛ نه MariaDB، نه php-mysql
docker daemon                      → بالا نیست
```

و فهرست آزمون‌های اجباری همین بخش، بیشترش **بی سایت زنده معنا ندارد**:
اندازه‌گیری واقعی تأخیر، «سایت پایین حین فروش»، تحویل تکراری، دو پیام
خارج از ترتیب، HPOS، چرخهٔ عمر افزونه.

تصمیم اولیه این بود: **ADR نوشته شد، کد نه.** مالک بعداً گفت ساخته شود،
و ساخته شد — ولی **آن مانع سر جایش است** و این را نباید پنهان کرد:

⚠️ **گیرندهٔ تست یکپارچه ووکامرس نیست.** یک سرور HTTP محلی است که همان
   الگوریتم `class-lmc-push-receiver.php` را پیاده کرده. پس ثابت می‌کند
   **قرارداد دو طرف می‌خواند** و ترتیب و تکرار درست مدیریت می‌شوند؛ ثابت
   **نمی‌کند** که افزونه روی یک وردپرس واقعی فعال می‌شود، HPOS را درست
   می‌بیند، یا `wc_get_product` در عمل همان رفتار را دارد.

⚠️ و این‌ها از فهرست شرط پذیرش **هنوز سنجیده نشده‌اند**، چون بی سایت
   زنده معنا ندارند:

       · تأخیر واقعی فروش تا تغییر ویترین (p50/p95)
       · چرخهٔ عمر افزونه: فعال/غیرفعال، به‌روزرسانی، HPOS
       · رفتار واقعی ووکامرس با `set_stock_quantity` و کش ویترین

   بقیهٔ آن فهرست — تکرار، ترتیب، تجمیع، سایت پایین، امضا، Replay،
   SSRF، Redirect، نامهٔ مرده، پیکربندی ناسازگار — سنجیده شده‌اند.

«Mock را Integration ننام» سر جایش است: این تست **قرارداد** را می‌سنجد و
اسمش هم همین است.

## شرط پذیرش — همان فهرستی که پیش از Merge باید سبز شود

```
· فروش حضوری → تأخیر واقعی تا تغییر موجودی سایت، p50/p95 ثبت شود
· فروش آخرین قلم → سایت **ناموجود** شود، نه «۰ ولی instock»
· سایت پایین حین فروش → فروش کامل شود؛ پیام در صف بماند؛ بعد برود
· تحویل تکراری همان پیام → موجودی دو بار کم نشود (اثبات مقدار مطلق)
· دو پیام خارج از ترتیب → عدد قدیمی، جدید را بازنویسی نکند
· ۵۰ فروش پشت سر هم → تجمیع کار کند و صف منفجر نشود
· مرجوعی / رسید خرید / انتقال / انبارگردانی → همه پیام بسازند
· تغییر قیمت از `catalog.set_price()` → لحظه‌ای؛ و null ≠ صفر
· امضای غلط / Replay / Payload دست‌کاری‌شده → ۴۰۱ یا ۴۰۳
· مقصد داخلی و Redirect داخلی → رد (SSRF)
· کشتن Worker وسط ارسال → پس از پایان اجاره دوباره برداشته شود
· پیام مسموم → نامهٔ مرده بگیرد و صف را قفل نکند
· چرخهٔ تطبیق → واگرایی دست‌سازِ سایت را **گزارش** کند
· بودجهٔ ۱۰۰ms صندوق پس از این تغییر همچنان رعایت شود (بخش ۸٫۸)
```

## پیامدها

**مثبت**
- پنجرهٔ Oversell از ۱۵ دقیقه به چند ثانیه.
- بی زیرساخت تازه: یک `topic` و یک مسیر REST.
- پوشش کامل تضمین‌شده، چون نقطهٔ اتصال `apply_movement()` است.

**منفی**
- یک مسیر REST **دریافت‌کننده** در افزونه = سطح حملهٔ تازه. بند ۵ و ۶
  همین سند کل هزینهٔ طراحی را همین‌جا می‌پردازد.
- صف شلوغ‌تر می‌شود؛ `outbox_dead` باید واقعاً نگاه شود
  (`deploy.sh status` از قبل نشانش می‌دهد).
- یک ایندکس یکتای جزئی تازه روی `outbox_message` که هزینهٔ درج دارد —
  ناچیز در حجم این کسب‌وکار، ولی صفر نیست.
