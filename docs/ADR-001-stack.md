# ADR-001 — انتخاب پشته فناوری

**وضعیت:** پذیرفته‌شده · **تاریخ:** شهریور ۱۴۰۵

## زمینه

سند اولیه ASP.NET Core + React پیشنهاد کرده بود. آن انتخاب با فرض یک تیم توسعه
نوشته شده بود. حالا که پروژه توسط یک نفر (Claude) نوشته و توسط مالک کسب‌وکار
بهره‌برداری می‌شود، معیارها عوض می‌شوند:

1. سادگی بهره‌برداری روی یک سرور — مالک، DevOps نیست.
2. کمترین تعداد اکوسیستم برای نگهداری.
3. قابلیت تحویل به توسعه‌دهنده بعدی.
4. **صحت مالی بالاتر از هر چیز دیگر.**

## تصمیم

### پایگاه داده: PostgreSQL — و قواعد مالی داخل خود دیتابیس

این مهم‌ترین بخش این ADR است.

قواعد حیاتی مالی به‌جای اینکه فقط در کد اپلیکیشن باشند، به‌صورت
**Constraint، Trigger و Function** در دیتابیس پیاده شده‌اند:

| قاعده | مکانیزم |
| --- | --- |
| هر سند باید متوازن باشد | `CONSTRAINT TRIGGER` معوق روی `journal_line` |
| حرکت انبار تغییرناپذیر است | Trigger روی `UPDATE`/`DELETE` |
| سند نهایی حذف نمی‌شود | Trigger روی `journal_entry` |
| لاگ حسابرسی فقط درج‌شدنی است | Trigger + زنجیره هش |
| موجودی منفی نمی‌شود | بررسی داخل `apply_movement` |
| فروش هم‌زمان اثر تکراری نمی‌سازد | `SELECT … FOR UPDATE` روی `stock_balance` |
| سند در دوره بسته ثبت نمی‌شود | Trigger روی `fiscal_year.status` |

**چرا:** یک باگ در لایه اپلیکیشن نباید بتواند دفتر را خراب کند. اگر روزی
اسکریپتی، یک ابزار مهاجرت، یا نسخه بعدی کد اشتباه کند، دیتابیس جلویش را
می‌گیرد. برای سیستمی که سود و مالیات یک کسب‌وکار واقعی را حساب می‌کند،
این لایه دفاعی ارزش هزینه‌اش را دارد.

**نتیجه جانبی:** این بخش مستقل از زبان است. اگر روزی تصمیم بگیرید کل لایه
اپلیکیشن را با چیز دیگری بازنویسی کنید، قواعد مالی سر جایشان می‌مانند.

### پول: `NUMERIC(18,0)` ریالی

- ذخیره به **ریال، عدد صحیح، بدون اعشار**. نمایش به تومان (÷۱۰) فقط در UI.
- هیچ‌جا `float` یا `double` نیست — نه در SQL، نه در TypeScript.
- در TypeScript پول با `bigint` نگه داشته می‌شود و در JSON به‌صورت **رشته**
  رد و بدل می‌شود (چون `number` جاوااسکریپت بالای ۹ کوادریلیون دقت را از
  دست می‌دهد، و مبالغ ریالی سریع بزرگ می‌شوند).

### لایه اپلیکیشن: TypeScript سرتاسری

- **API:** Node 22 + Fastify + **Kysely** (کوئری‌بیلدر Type-safe، نه ORM سنگین)
- **UI:** React + TypeScript + Vite، RTL کامل
- **Worker:** همان کدبیس، پردازش Outbox
- **مهاجرت‌ها:** فایل‌های SQL خام و شماره‌دار — نه مهاجرت تولیدشده توسط ORM

**چرا Kysely و نه Prisma یا TypeORM:** برای عملیات مالی به SQL صریح نیاز
است — `FOR UPDATE`، CTE، توابع تجمیعی گزارش‌ها. ORMها این‌ها را پنهان یا
سخت می‌کنند. Kysely تایپ کامل می‌دهد بدون اینکه SQL را از دست بدهید.

**چرا مهاجرت SQL خام:** برای یک سیستم مالی، تاریخچه تغییرات اسکیما باید
قابل خواندن و حسابرسی باشد. مهاجرت تولیدشده توسط ORM هیچ‌کدام نیست.

**چرا نه ASP.NET:** یک زبان به‌جای دو، یک زنجیره ابزار به‌جای دو، تایپ
مشترک میان API و UI. برای یک نفر، این تفاوت معناداری در سرعت است.
اگر روزی به توسعه‌دهنده ایرانی سپرده شود، بخش سنگین منطق مالی در SQL است
که هر توسعه‌دهنده‌ای می‌خواند — نه در یک فریم‌ورک خاص.

### استقرار: Docker Compose روی یک سرور

`postgres` + `api` + `web` + `worker` + `caddy` (TLS خودکار).
بدون Kubernetes، بدون Redis، بدون صف‌ساز جداگانه — تا زمانی که نیاز واقعی
اثبات نشود.

## پیامدها

**مثبت**
- بخش حیاتی (منطق مالی) همین حالا نوشته، اجرا و تست شده است.
- تصمیم‌های باز (کدینگ، نرخ مالیات، سقف تخفیف) داده‌اند نه کد.
- تغییر Stack اپلیکیشن در آینده، منطق مالی را از بین نمی‌برد.

**منفی**
- منطق در دیتابیس، دیباگ و نسخه‌بندی سخت‌تری از کد اپلیکیشن دارد.
  → کاهش‌دهنده: مهاجرت‌های شماره‌دار و مجموعه تست SQL که در CI اجرا می‌شود.
- توسعه‌دهنده بعدی باید PL/pgSQL بلد باشد.
  → کاهش‌دهنده: توابع کم، متمرکز و کامنت‌گذاری‌شده به فارسی‌اند.
