# مرز قرارداد درگاه‌ها — ۲۰۲۶/۱۰/۰۲

برش نخست آداپتور مستقل سمت سرور بود. برش بعدی، پیکربندی محیطی معتبر، انتقال HTTPS
و مسیر تشخیص احراز را در [قرارداد runtime](PAYMENT-PROVIDER-RUNTIME.md) اضافه می‌کند؛
هنوز UI، مهاجرت، ثبت وجه، سند یا شاهد اتصال واقعی درگاه وجود ندارد. اسنپ‌پی فعلی در
`sales/invoice.ts` و `http/snappay-routes.ts` **ثبت دستی** با حساب شعبه و مرجع
است و همچنان همین معنا را دارد. شمارهٔ مهاجرت این برش ندارد.

## شواهد رسمی

- [اسنپ‌پی self-cms، ویرایش ۲٫۱](https://academy.snapppay.ir/self-cms/):
  متن و نمونه‌های embedded درخواست/پاسخ در تاریخ بالا خوانده شد. فصل‌های ۳–۸،
  ۱۰–۱۳ مبنای پیاده‌سازی هستند. HTML عمومی در `tmp/provider-contracts` محلی
  نگه داشته شده؛ بخشی از artifact انتشار نیست.
- [دریافت اطلاعات فنی پذیرنده](https://academy.snapppay.ir/2026/06/06/snapppay-gateway-tech-guide/):
  Base URL و چهار credential از پنل پذیرنده می‌آیند؛ میزبان تولید حدس زده نشده است.
- [مستند UPG دیجی‌پی](https://www.mydigipay.com/developers/docs/upg/?php=):
  تلاش خواندن مستقیم با 504 و timeout مواجه شد. متن دقیق درخواست/پاسخ در این
  برش در دسترس نبود؛ خلاصهٔ پژوهش قبلی برای ساخت قرارداد کافی نیست.

صفحهٔ محصول حضوری اسنپ‌پی و معرفی لینک پرداخت، دلیل پشتیبانی API آنلاین از
کانال حضوری یا لینک عمومی نیستند. `requireSupportedChannel` تمام کانال‌ها جز
آنلاین اسنپ‌پی و فعلاً تمام دیجی‌پی را با `unsupported` رد می‌کند.

## آنچه ساخته شده

`apps/api/src/payments/providers/snappay.ts` با انتقال‌دهندهٔ تزریق‌شده:

| متد | قرارداد HTTP | نتیجهٔ قابل استفاده در ادغام |
|---|---|---|
| `authenticate` | POST `/api/online/v1/oauth/token`، Basic و فرم password/online-merchant | access token فقط برای سرور؛ بدون ذخیره یا refresh خودکار |
| `eligible` | GET `/api/online/offer/v1/eligible` | مبلغ IRR، روش‌های مجاز اختیاری؛ متن پیشنهاد از پاسخ درگاه |
| `createToken` | POST `/api/online/payment/v1/token` | paymentToken و paymentPageUrl، وضعیت pending؛ هیچ اثر مالی |
| `verify` | POST `/api/online/payment/v1/verify` | verified، **نیازمند settle** |
| `settle` | POST `/api/online/payment/v1/settle` | settled؛ هنوز ثبت مالی در این ماژول وجود ندارد |
| `status` | GET `/api/online/payment/v1/status?paymentToken=…` | تطبیق transactionId و مبلغ، یکی از پنج وضعیت مستند |
| `cancel` | POST `/api/online/payment/v1/cancel` | فقط Snapshot تسویه‌شده؛ نتیجهٔ cancel، بدون برگ مالی خودکار |

مبالغ در ورودی/خروجی داخلی رشتهٔ صحیح ریال، تا سقف `NUMERIC(18,0)` هستند.
ارسال به API عدد صحیح JSON است، با BigInt و بدون تبدیل به Number. برای پاسخ
استعلام، متن اصلی JSON مبلغ با context.source در Node 22+ خوانده می‌شود؛ نبود
این قابلیت باعث رد پاسخ می‌شود. مبلغ 900719925474099301 با همسایه‌اش یکی نمی‌شود.
ورودی سبد باید از Snapshot محاسبه‌شدهٔ سرور بیاید؛ آداپتور فقط تطبیق مجموع اقلام،
حمل، مالیات، تخفیف و منبع خارجی را طبق قرارداد می‌سنجد.

فقط زیرمجموعهٔ روشن شناسهٔ تراکنش (۵ تا ۱۰ رقم) پذیرفته می‌شود. سند برای شناسهٔ
بیش از ۱۰ رقم وجود حرف را می‌خواهد، ولی قواعد کامل طول/الفبا را نمی‌گوید؛ نمونهٔ
callback نیز متنی خط‌تیره‌دار است. این زیرمجموعه عامدانه محدود است. پاسخ‌های
verify/settle/cancel فیلد transactionId دارند ولی معنای مستقل provider ID تعریف
نشده؛ پیاده‌سازی آن را با شناسهٔ ذخیره‌شده تطبیق می‌دهد و در اختلاف نامعلوم
می‌ماند. تطبیق این برداشت با پاسخ محیط stage، پیش‌نیاز فعال‌سازی است.

## مرز تحویل به B: قصد پایدار و اثر مالی دقیقاً یک‌بار

1. قبل از شبکه، شناسهٔ یکتای تلاش، provider/channel، مبلغ ریالی، snapshot سبد،
   فاکتور، شعبه و hash قصد را پایدار کنید. هر تب طبق قرارداد شناسهٔ جدا می‌خواهد؛
   تکرار یک قصد در اثر timeout نباید تلاش جدید بسازد. یکتایی ۵–۱۰ رقم را DB
   تضمین کند؛ این آداپتور شناسه تولید نمی‌کند.
2. تنها پس از eligibility مثبت و انتخاب واقعی کاربر توکن بخواهید. خروجی توکن را
   پیش از redirect ذخیره کنید. timeout توکن بدون paymentToken با status فعلی
   قابل جست‌وجو نیست؛ قرارداد inquiry با transactionId پیدا نشده، پس بررسی
   دستی/پشتیبانی لازم است و صدور توکن جدید خودکار ممنوع است.
3. callback فقط POST و با `parseSnappayCallback` خوانده شود. transactionId و
   amount باید با تلاش ذخیره‌شده تطبیق کنند. خروجی همیشه `untrusted_callback`
   است؛ حتی OK وجه محسوب نمی‌شود. تکرار callback همان خروجی نامطمئن را می‌دهد.
4. claim پایدار/قفل و inbox یکتا در B باید فراخوانی Verify ناشی از callbackهای
   هم‌زمان را تک‌بار کند؛ این ماژول بدون DB چنین تضمینی ندارد. Snapshot stale
   نباید اجازهٔ Verify دوباره بدهد. verified/settled در ورودی Verify رد می‌شود.
5. Verify موفق به‌تنهایی کافی نیست؛ Settle الزامی است. timeout، HTTP ناموفق،
   successful:false، پاسخ خراب/شناسهٔ متفاوت همگی `unknown` هستند؛ وجه ثبت نشود.
   هیچ retry، refresh، inquiry یا تلاش جدید خودکار در آداپتور انجام نمی‌شود.
6. برای نامعلومِ دارای paymentToken استعلام کنید. VERIFY مجوز اقدام settle و
   PENDING در جریان Verify مجوز تصمیم آگاهانه برای تکرار همان Verify است؛ SETTLE
   حالت نهایی اعلام‌شدهٔ درگاه است. پیش از تکرار، وضعیت inquiry و همان شناسهٔ قصد
   پایدار شود. CANCEL/REVERT وجه دریافتی جدید ایجاد نمی‌کنند.
7. فقط نتیجهٔ معتبر settle یا status=SETTLE با تطبیق تلاش، به مسیر once-only ثبت
   مالی B تحویل شود. transactionId/attempt یکتا، تراکنش DB و بازیابی crash را B
   تضمین کند. بازگشت Cancel نیز به قصد مستقل برگشت و سند رسمی نیاز دارد.

`ProviderTransport` باید server-only، بدون لاگ credential/بدنه/URL توکن‌دار، بدون
retry و با رد redirect باشد. آداپتور `redirect:error` و AbortSignal می‌فرستد و
خودش حتی برای transport بی‌توجه به abort سقف انتظار ۳۰ ثانیه دارد. خطای خام و
پاسخ خطا بیرون نمی‌روند. baseUrl، returnUrl و origin مجاز صفحهٔ پرداخت فقط از
تنظیم مورد اعتماد سرور؛ هرگز callback یا درخواست مرورگر. هیچ transport زنده
پیش‌فرض در آداپتور وجود ندارد. runtime جدید فقط با تنظیم کامل و حالت صریح diagnostic
انتقال واقعی را برای تشخیص احراز فراهم می‌کند؛ endpoint عمومی یا اجرای مالی ندارد.

## عمداً بسته و باقی‌مانده

- Revert: جدول callback می‌گوید FAILED به Revert نیاز دارد، اما فصل ۹ می‌گوید
  پیاده‌سازی لازم نیست مگر اطلاع پشتیبانی؛ متن بعدی هم سناریوی OK بدون امکان
  ارائهٔ خدمت را ذکر می‌کند. `revert()` تا رفع تعارض با پشتیبانی unsupported است.
- Update: قرارداد کاهش مبلغ/تغییر اقلام وجود دارد، اما در این برش متد شبکه ساخته
  نشده است؛ `update()` unsupported است. قصد پایدار تعدیل و آشتی مبلغ/فاکتور لازم است.
- forcedPaymentMethodTypes: نیازمند فعال‌سازی پذیرنده است؛ این گزینه در payload
  ساخته‌شده پشتیبانی نمی‌شود و فیلد اضافی ورودی رد می‌شود.
- دیجی‌پی: auth/refresh، ticket، callback با amount/providerId، verify، deliver
  برای CREDIT/BNPL، refund و inquiry باید از متن دقیق قرارداد فعلی دوباره خوانده
  شوند. هیچ‌کدام پیاده یا تأیید نشده‌اند؛ آزمون تطبیق providerId دیجی‌پی نیز
  ادعا نمی‌شود. تحویل کالا پیش از مرحلهٔ لازم deliver نباید از خلاصهٔ پژوهش حدس زده شود.
- حضوری، بارکد، لینک اشتراکی، statement تسویه و inquiry عمومی خرید گم‌شده هیچ
  قابلیت اثبات‌شده‌ای در این برش ندارند.
- دسترسی stage، whitelist IP/return URL، credentials، آزمون واقعی و تأیید فنی
  پذیرنده، امنیت transport، ادغام پایدار B و بازبینی مستقل هنوز لازم‌اند.

آزمون‌ها با پاسخ‌های literal مصنوعی منطبق بر نمونه‌های رسمی، بدون شبکه، مبلغ
بزرگ/دست‌کاری‌شده، شناسهٔ نادرست، callback تکراری، ترتیب Verify/Settle/Cancel،
timeout، عدم retry، پالایش خطا و کانال unsupported را می‌سنجند. این شواهد قرارداد
محلی است؛ تأیید اتصال واقعی یا آمادگی تولید نیست.
