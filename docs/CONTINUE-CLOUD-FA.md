# پرامپت کامل ادامهٔ Labelmod در Codex Cloud

در مخزن `AliJ021/labelmod-core` ادامه بده و فارسی گزارش کن. این انتقال برای ادامهٔ کار ناتمام است؛ از ابتدا بازنویسی نکن و برای مراحل مجاز منتظر «ادامه بده» نمان.

## ابتدا نسخه و وضعیت را تطبیق بده

1. PR https://github.com/AliJ021/labelmod-core/pull/105 و شاخهٔ `feat/ux-workspace-20260926` را بخوان. اگر هنوز باز است همان head تازه را مبنا بگیر؛ اگر merge شده، main شامل آن را مبنا قرار بده. snapshot آزموده‌شدهٔ قبل از تکمیل این مستندات `9098598e7d816b9220002ecb3f6a9fc446240018` است؛ این SHA را آخرین head فرض نکن. تغییر چت دیگری را overwrite یا force-push نکن.
2. `docs/HANDOFF-2026-09-26-FA.md`، `docs/SECURITY-FINDINGS-HANDOFF-2026-09-26.md`، `docs/WEB-WORKSPACE-AUDIT.md`، `docs/WEB-BACKUP-RESTORE.md`، README، CLAUDE، AGENTS در صورت وجود و قواعد مخزن را کامل بخوان. این‌ها داخل PR هستند و ZIP لازم نیست. نام قدیمی یک patch یا «تغییر ثبت‌نشده» در snapshot محلی مجوز اعمال دوباره نیست؛ کد قدیمی با تاریخچه تطبیق داده شده است.
3. همهٔ PRهای باز را با همهٔ نویسندگان جست‌وجو کن؛ فیلتر فقط PRهای مالک، Dependabot را جا می‌اندازد. در بازبینی تحویل، #102، #103، #104 و #105 باز بودند. diff نسبت به base واقعی، CI آخرین SHA، reviewها و inline threadهای حل‌نشده را بخوان. نتیجهٔ CI قبلی را به head تازه تعمیم نده و علت قرمز را از خطای واقعی استخراج کن.

## چه چیزهایی انجام شده و نباید تکرار شود

بازطراحی React/Vite با رابط فارسی RTL، ناوبری دسکتاپ/موبایل، URL صفحات، جست‌وجوی بخش‌ها، ورودی واحد نام/کد/بارکد با محصول مادر و انتخاب رنگ/سایز، کنترل تراکنشی موجودی بدون رزرو، حفظ هویت retry و مالکیت/شیفت پیش‌نویس، مرکز فاکتورها و چاپ، گزارش ثبت‌کننده/نهایی‌کننده و اسنپ‌پی دستی پیاده شده‌اند. migrations 079 تا 082 افزایشی‌اند؛ قفل و scope ثبت گروهی سند اصلاح شده‌اند. کد و قالب سرویس مستقل بکاپ حاضر است ولی سرویس نصب و پذیرفته نشده است.

PRهای #94 تا #101 در مبنای فعلی حفظ شده‌اند؛ #101 ادغام و کدش در نسخهٔ تست مستقر شده است. #63 و #93 و اصلاحات قدیمی حسابداری را دوباره اجرا نکن. ده سند اصلاحی تاریخی و فروش/مرجوعی‌های آزمایشی قبلی دوباره ساخته نشوند. شماره‌های F1…F25/I1…I4 حسابداری را با ردیف‌های امنیتی اشتباه نگیر. دفتر امنیت 49 ردیف دارد؛ 49 تکرار موضوع 25 است، نه کار تازه.

نسخهٔ جدید روی سرور آزمایشی کاربر مستقر شده، اما checkout قدیمی سرور معرف runtime نیست: release و compose override جدا دارد. قبل از هر انتشار، image، mount و تنظیمات فعال را فقط‌خواندنی بررسی کن؛ اجرای compose از checkout قدیمی ممکن است نسخه را برگرداند. اطلاعات ورود، میزبان و مسیر خصوصی بکاپ عمداً در Git نیستند. اگر اتصال/secret در Cloud در دسترس نیست، کار کد و CI را ادامه بده و فقط آزمون زندهٔ وابسته را «اجرانشده» ثبت کن.

## موانع فعلی و ترتیب ادامه

- در #105 روی SHA `9098598`، سه job DB/API، build و Woo موفق بودند؛ مرورگر 1127 موفق و 1 ناموفق بود. شکست WebKit dark 375 در آزمون lock/logout، assertion خطای مرورگر در fixtures و درخواست `auth/can?operation=period.close` است. trace و lifecycle mock/درخواست هنگام خروج را بررسی کن؛ خطا را ignore نکن و CORS سرور واقعی را بدون شاهد تغییر نده. اجرای محلی جدا هم با بسته‌شدن context مرورگر گزارش کامل موفق ندارد.
- یک سرریز افقی واقعی در reports/manager در عرض 375 تأیید شده است. ابتدا رفع و regression کن؛ سپس پذیرش تعاملی همهٔ صفحات/نقش‌ها، شش عرض 320/375/768/1024/1440/1920، Chromium/WebKit، دو تم، کیبورد، zoom و صفحه‌کلید موبایل را تکمیل کن. page-load جای آزمون عملیات نیست.
- #102 ارتقای typescript-eslint است و یک شکست WebKit هنگام fontsReady داشت؛ #103 ارتقای ZXing است و 24 شکست decode بارکد داشت؛ #104 ارتقای Zod است و آزمون مرورگر لغو شده بود. همه هنگام بررسی mergeable=false بودند. علت/تعارض فعلی را تازه بررسی کن. fixture دوربین با UUID معتبر در #105 اصلاح شده؛ این هم‌پوشانی را قبل از نسبت‌دادن خطا به ZXing لحاظ کن. سه PR lockfile مشترک دارند؛ ترکیب نهایی را هم تست کن.
- کنترل موجودی یک‌عددی و replay در API زنده موفق بوده، ولی دو صندوق هم‌زمان، قطع پاسخ، سطرهای تکراری، پیش‌نویس پرداخت‌دار، تغییر کاربر/شیفت بسته و پیام کنار قلم باید کامل پذیرفته شوند. بدون رزرو، کنترل نهایی لازم می‌ماند. اسکن/دوربین نباید دوبار قلم اضافه کنند.
- گزارش کاربران و اسنپ‌پی را با دفتر/دریافت/مرجوعی تطبیق بده؛ ثبت‌کننده و نهایی‌کننده جدا و هویت تاریخی بی‌شاهد نامعلوم بماند. اسنپ‌پی فقط ثبت دستی پرداخت تأییدشده با شمارهٔ پیگیری و حساب تسویهٔ معتبر است. مجوز نقش فقط‌گزارش برای مرکز فاکتورها را بررسی کن؛ برای موفق‌شدن تست دسترسی را بی‌دلیل باز نکن.
- مدیر بکاپ پیش از نصب، بازبینی امنیتی و تمرین مستقل قطع، rollback، دو عملیات هم‌زمان، مصرف عامل دوم، audit، حفظ مجوزهای جاری، ابطال نشست‌ها و توقف خروجی‌ها می‌خواهد. API عمومی مالک دیتابیس، Docker socket یا فرمان آزاد نگیرد. وجود تست PG به معنی پذیرش عملیاتی restore نیست.
- دفتر امنیتی را سطر به سطر نگه دار: 3/16/17/20/25 اصلاح candidate #105 دارند؛ 4 برای حساب/مالیات هدیه منتظر تصمیم است؛ 29 قیود رسید/سفارش و 33/34/42 ارتقای نصب‌های تاریخی بازند. اصلاحات قبلی و مهارهای بدون تغییر 2/13/48 را دوباره پیاده نکن، اما شاهد قدیمی را تأیید همهٔ سناریوهای جدید ندان.
- اختتام/افتتاح/بازگشایی کامل سال، Woo در قطعی طولانی و reconcile، مرجوعی مبلغی بدون قلم و سفارش قدیمی بدون نگاشت، چرخهٔ تأیید/رد دستی مرجوعی سایت، بازیابی روی میزبان دوم و پذیرش حسابدار هنوز باید طبق سند تحویل تکمیل شوند. full-stack clone و سناریوی پنج فروش تاریخی قبلاً آزموده شده‌اند؛ آثار مالی آن‌ها را دوباره نساز. مشاهدهٔ تاریخچه با تأخیر چندثانیه‌ای، refresh خودکار صفحه یا تأخیر صفر را ثابت نمی‌کند.

## محدودیت‌ها و تصمیم‌های تأییدشده

- Bardia و recovery_admin هرگز فعال یا بازسازی نشوند. seed/reset روی دفتر اصلی یا DB موجود ممنوع است؛ migration اجراشده، اسناد قطعی، گردش انبار و حسابرسی را بازنویسی نکن. اصلاح مالی از مسیر رسمی append-only باشد.
- هیچ تستی برای سبزکردن CI ضعیف، حذف یا skip نشود. اسرار، نشست، بکاپ و دادهٔ مشتری وارد Git/PR/گزارش نشوند. Computer Use استفاده نکن؛ CLI/API و Playwright مجازند.
- تست مشخص و استقرار روی سرور آزمایشی مجاز است؛ آزمون مخرب ابتدا روی کپی مستقل با خروجی خارجی مسدود انجام شود. هر restore اصلی باید زمان دقیق بکاپ و داده‌های برگشتی را نشان دهد و تأیید همان عملیات را بگیرد. ارسال واقعی پیامک و پرداخت بانکی مجاز نیستند.
- تغییر عمدهٔ جدید رفتار مالی/معماری را ساده توضیح بده و تأیید بگیر. جهت‌های تأییدشده: مرجوعی سایت قبل از اثر مالی/موجودی به تأیید مستقل انسانی نیاز دارد؛ اقلام تازهٔ پیش‌نویس قیمت زمان افزودن و اقلام قبلی قیمت محفوظ دارند؛ برگشت هدیه مبلغ صریح کاربر مجاز است و مجموع آن از هزینهٔ ذخیره‌شدهٔ فاکتور بیشتر نمی‌شود، ولی حساب/مالیات هنوز نامشخص است؛ رسید چندنرخی یک SKU تا تعیین قاعده قطعی نشود. کنترل موجودی بدون رزرو، اسنپ‌پی دستی و سرویس جدا برای restore نیز تأیید شده‌اند.
- محیط Woo آزمایشی است؛ Guard و محدودیت خروجی حفظ شوند. برای مشکل دسترسی، allow-all یا دورزدن WAF انجام نده. دستگاه تازهٔ بدون شعبه فقط با مدیر سراسری تخصیص بگیرد؛ مدیریت شعبه‌ای خارج از همان شعبه باز نشود.

## پذیرش و تحویل بعدی

ابتدا regression مرتبط، سپس مجموعهٔ کامل SQL، API با نقش مالک و app محدود، واحد وب، مرورگر، Woo/PHP، build image و audit وابستگی‌ها را روی نسخهٔ دقیق اجرا کن. DB تست مستقل، Node22+، pnpm10.33.0، PostgreSQL16/client هم‌نسخه و PHP mbstring لازم‌اند؛ فرمان‌های سند تحویل و workflow فعلی مرجع‌اند.

چاپگر MEVA TP-UNW و لیبل‌زن کابلی Bixolon XD3-40T روی رایانهٔ صندوق باید در مقیاس 100٪ با کاغذ واقعی آزموده شوند؛ ابعاد رول/کابل و مدل بارکدخوان را هنوز باید مشخص کرد. اقتصادنوین نام بانک است؛ مدل پایانه/PSP/SDK معلوم نیست. زیبال، سرویس مالیاتی، دفتر مستقل کارت هدیه و تحویل واقعی ملی‌پیامک پذیرش مستقل دارند. کاربر تحویل SMS را به بعد موکول کرده؛ دوباره برای ارسال اصرار نکن.

پس از رفع موانع، بررسی همهٔ jobها/reviewها و اثبات آمادگی روی آخرین SHA، ادغام PRهای مجاز را انجام بده؛ mergeable بودن یا فقط سبزی unit test کافی نیست. اگر هنوز مانع معتبر هست، PR را باز نگه دار و علت دقیق را ثبت کن. با هر تحویل، راهنمای مخزن و همین پرامپت را هم‌زمان به‌روز کن. کار پیاده‌شده، آزموده‌شده، مستقرشده و پذیرفته‌شده را جدا گزارش بده؛ هیچ ادعای «صددرصد بدون مشکل» بدون شاهد نکن.
