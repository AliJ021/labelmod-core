# مشخصات امنیتی — Label Mod Core

**وضعیت:** الزام‌آور · **مبنا:** وضعیت توصیه‌های امنیتی ۲۰۲۶

این سند تصمیم‌های امنیتی را قفل می‌کند. هر انحرافی از این‌ها باید در یک ADR
جداگانه توجیه شود.

قاعده حاکم: **این سیستم پول و اسناد مالی یک کسب‌وکار واقعی را نگه می‌دارد.**
جایی که میان راحتی و صحت مالی تعارض هست، صحت برنده است.

## ۱. رمز عبور و احراز هویت پرسنل

### الگوریتم درهم‌سازی: Argon2id

MD5، SHA-1، SHA-256 خام، bcrypt و PBKDF2 برای رمز جدید ممنوع‌اند.

```
Argon2id
  memory  = 65536 KiB   (۶۴ مگابایت)
  time    = 3
  paralel = 4
  salt    = ۱۶ بایت تصادفی، یکتا برای هر کاربر
  output  = ۳۲ بایت
```

حداقل قابل قبول OWASP برای Argon2id `m=47104, t=1, p=1` است. چون حجم لاگین
اینجا پایین است (چند نفر پرسنل)، پارامتر بالاتر انتخاب شده.

**تنظیم عملی:** روی سرور واقعی زمان بگیرید. هدف **۲۵۰ تا ۵۰۰ میلی‌ثانیه**
برای هر بار درهم‌سازی. اگر خیلی سریع‌تر بود، `memory` را بالا ببرید.

### PIN صندوق‌دار — جایی که اکثر سیستم‌های POS اشتباه می‌کنند

یک PIN چهاررقمی ۱۰٬۰۰۰ حالت دارد. **هیچ الگوریتم درهم‌سازی‌ای این را نجات
نمی‌دهد.** دفاع واقعی جای دیگری است:

1. PIN فقط روی **دستگاه ثبت‌شده و تأییدشده** کار می‌کند.
2. PIN فقط **پس از یک ورود کامل در همان روز** فعال می‌شود — یعنی PIN برای
   باز کردن قفل نشست موجود است، نه برای ساختن نشست جدید.
3. **۵ تلاش ناموفق → قفل ۱۵ دقیقه‌ای** روی همان کاربر و همان دستگاه.
4. **PIN هرگز عملیات حساس را مجاز نمی‌کند.** بازپرداخت، ابطال فاکتور، تغییر
   قیمت و اصلاح موجودی نیازمند احراز هویت کامل مجدد است — نه PIN.

### نشست: توکن مات، نه JWT

بند ۶ سند اصلی «خروج اجباری همه نشست‌ها و قطع دسترسی گوشی مفقودی» را الزام
کرده. **JWT این را نمی‌تواند** — یک JWT صادرشده تا انقضایش معتبر است و
باطل‌کردنش نیازمند فهرست ابطال سمت سرور است، که آن‌وقت همان نشست سمت سرور
است با پیچیدگی اضافه.

```
توکن نشست = ۳۲ بایت تصادفی امن (crypto.randomBytes)
ذخیره در DB = SHA-256 توکن، نه خود توکن
کوکی        = HttpOnly · Secure · SameSite=Strict · Path=/
عمر         = ۱۲ ساعت پرسنل · ۳۰ روز مشتری با تمدید چرخشی
```

باطل‌کردن یک نشست یا همه نشست‌های یک کاربر = یک `DELETE`. تمام.

### احراز هویت دومرحله‌ای مدیر و حسابدار

**اولویت اول: WebAuthn / Passkey.** در ۲۰۲۶ روی همه مرورگرها و گوشی‌های
رایج در دسترس است و برخلاف TOTP **در برابر فیشینگ مقاوم است** — کلید به
دامنه گره خورده، پس صفحه جعلی نمی‌تواند از آن استفاده کند.

**پشتیبان: TOTP** (RFC 6238، ۶ رقم، پنجره ۳۰ ثانیه، تحمل ±۱ گام) برای وقتی
دستگاه Passkey در دسترس نیست. کدهای بازیابی یک‌بارمصرف، درهم‌شده ذخیره شوند.

### OTP مشتری

```
طول        = ۶ رقم، از مولد امن (نه Math.random)
عمر        = ۱۲۰ ثانیه
تلاش مجاز  = ۳، سپس ابطال کد
محدودیت نرخ = ۳ کد در ۱۵ دقیقه برای هر شماره + سقف جداگانه برای هر IP
مقایسه     = زمان‌ثابت (timingSafeEqual)
لاگ        = کد هرگز در لاگ، Sentry یا پیام خطا ظاهر نمی‌شود
```

## ۲. انتقال

- **TLS 1.3 و بالاتر.** TLS 1.0/1.1/1.2 غیرفعال.
- **HSTS** با `max-age=31536000; includeSubDomains`.
- گواهی خودکار از Let's Encrypt توسط Caddy.

### تبادل کلید مقاوم در برابر کوانتوم

روی Reverse Proxy، تبادل کلید ترکیبی **X25519MLKEM768** فعال شود.

**چرا:** اسناد مالی عمر محرمانگی طولانی دارند. تهدید «امروز جمع کن، فردا
رمزگشایی کن» یعنی ترافیکی که امروز شنود شود، ممکن است سال‌ها بعد باز شود.
در ۲۰۲۶ این حالت ترکیبی در مرورگرهای رایج پیش‌فرض است و **هزینه‌اش عملاً صفر**
— چند صد بایت اضافه در Handshake.

این ریسک درجه‌اول شما نیست (آن رمز ضعیف و توکن لو رفته است)، ولی چون رایگان
است، روشنش کنید.

## ۳. داده

| قاعده | وضعیت |
|---|---|
| پول هرگز float — `NUMERIC(18,0)` ریالی | ✅ اعمال‌شده در اسکیما |
| شماره کامل کارت بانکی هرگز ذخیره نمی‌شود | فقط `ref_no` پیگیری |
| CVV و رمز دوم هرگز، حتی موقت، ذخیره نمی‌شوند | — |
| داده اندازه مشتری اختیاری و قابل حذف | ✅ در مدل داده |
| رضایت بازاریابی صریح و قابل بازپس‌گیری | ✅ `consent_*` |
| لاگ حسابرسی فقط درج‌شدنی با زنجیره هش | ✅ اعمال‌شده |

### نقش‌های پایگاه داده

نقش اپلیکیشن **مالک اسکیما نیست**:

```sql
-- بدون DDL
REVOKE CREATE ON SCHEMA platform,identity,catalog,inventory,
                        purchasing,sales,treasury,ledger FROM labelmod_app;

-- بدون حذف روی جداول تغییرناپذیر (علاوه بر Trigger — دو لایه دفاع)
REVOKE UPDATE, DELETE ON platform.audit_log        FROM labelmod_app;
REVOKE UPDATE, DELETE ON inventory.stock_movement  FROM labelmod_app;
```

مهاجرت‌ها با نقش جداگانه `labelmod_migrator` اجرا می‌شوند.

### لنگر انداختن زنجیره حسابرسی

زنجیره هش دستکاری را قابل تشخیص می‌کند، ولی کسی که دسترسی کامل DB دارد
می‌تواند کل زنجیره را بازسازی کند. راه‌حل ارزان: **هر شب هش آخرین رکورد
`audit_log` در فایل بکاپ ذخیره شود.** بازنویسی تاریخچه آن‌وقت نیازمند
دستکاری بکاپ‌های خارج از سرور هم هست.

## ۴. بکاپ

```
رمزنگاری  = age یا gpg، پیش از خروج از سرور
مقصد      = خارج از سرور عملیاتی — بدون استثنا
نگهداری   = روزانه ۳۰ روز · هفتگی ۱۲ هفته · ماهانه ۱۲ ماه
کلید      = خارج از همان سرور و خارج از مخزن نگهداری شود
```

**تمرین Restore ماهانه اجباری است.** بکاپی که Restore آن تست نشده، بکاپ
نیست — یک فایل است با یک فرض.

`ops/restore-drill.sh` دامپ را در یک دیتابیس یک‌بارمصرف برمی‌گرداند و
هشت ادعا رویش می‌راند — از جمله زنجیره حسابرسی، حلقه‌به‌حلقه. سابقه در
`platform.restore_drill` (تغییرناپذیر) می‌نشیند و
`platform.restore_drill_status` عبور از `backup.restore_drill_days` را
`overdue` اعلام می‌کند؛ نبودِ هر تمرینی `never` است.

⚠️ تمرین **ناموفق** زنگ را خاموش نمی‌کند.

## ۵. زنجیره تأمین

بخشی که در ۲۰۲۶ بیشترین رشد حمله را داشته: نه خود کد شما، بلکه چیزهایی که
به آن وابسته است.

- `pnpm` با `pnpm-lock.yaml` **کامیت‌شده**. نصب در CI با `--frozen-lockfile`.
- **اکشن‌های GitHub به SHA کامل کامیت پین شوند، نه به تگ.** تگ قابل جابه‌جایی
  است؛ چند حادثه ربودن تگ نشان داد `@v4` تضمین نیست.

  ```bash
  # گرفتن SHA برای پین کردن
  git ls-remote https://github.com/actions/checkout refs/tags/v4
  ```

- `pnpm audit --prod` در CI، شکست بیلد روی آسیب‌پذیری High و بالاتر.
- Dependabot روشن.
- ایمیج پایه `node:22-alpine`، اجرا با کاربر **غیر root**.
- هیچ وابستگی‌ای بدون دلیل مشخص اضافه نمی‌شود. برای این پروژه، تعداد کم
  وابستگی خودش یک کنترل امنیتی است.

## ۶. لایه اپلیکیشن

- **اعتبارسنجی با Zod در هر مرز API.** هیچ ورودی بدون Schema وارد منطق نشود.
- **کوئری پارامتری، همیشه.** Kysely این را تضمین می‌کند. `sql.raw` با ورودی
  کاربر ممنوع مطلق.
- **CSP** بدون `unsafe-inline`، با nonce. `script-src` باید
  **`wasm-unsafe-eval`** هم داشته باشد: اسکنر بارکد موبایل روی
  مرورگرهای بدون `BarcodeDetector` بومی (از جمله آیفون) از WebAssembly
  استفاده می‌کند و CSP سخت‌گیرانه بدون این کلیدواژه، نمونه‌سازی آن را
  در Chromium می‌بندد. فایل WASM محلی سرو می‌شود، ولی محلی‌بودن جای
  اجازه اجرا را نمی‌گیرد.
- **CSRF:** `SameSite=Strict` به‌علاوه توکن Double-Submit روی هر درخواست
  تغییردهنده وضعیت.
- **محدودیت نرخ:** ورود (۵ در دقیقه بر IP) · ارسال OTP · endpointهای پرداخت.
- **پیام خطا:** «نام کاربری یا رمز اشتباه است» — هرگز مشخص نشود کدام‌یک.
- خطاها به کاربر بدون Stack Trace؛ جزئیات فقط در لاگ ساختاریافته با
  Correlation ID.

## ۷. آنچه امنیت نیست و نباید با آن اشتباه شود

- **الزام تعویض دوره‌ای رمز.** توصیه به‌روز خلافش است — باعث رمزهای ضعیف
  الگودار می‌شود. تعویض فقط هنگام نشانه نشت.
- **قواعد پیچیدگی رمز** (حتماً یک علامت، یک عدد بزرگ…). به‌جایش: **حداقل
  ۱۲ کاراکتر** و بررسی در برابر فهرست رمزهای لو رفته.
- **پنهان‌کردن نسخه‌ها و مسیرها** به‌عنوان تنها دفاع. Security by obscurity
  لایه هست، دفاع نیست.

## ۹. محدودیت پلن GitHub — و جایگزین آن

مخزن: `AliJ021/labelmod-core` — خصوصی، پلن Free.

جدول زیر **آزموده شده** است، نه حدس. تاریخ بررسی: شهریور ۱۴۰۵.

| قابلیت | وضعیت | پاسخ واقعی API |
|---|---|---|
| Repository rulesets | ❌ | `Upgrade to GitHub Pro or make this repository public` |
| Branch protection rules | ❌ | همان محدودیت |
| Secret scanning و Push protection | ❌ | `Secret scanning is not available for this repository` |
| Dependabot alerts | ✅ **فعال شد** | — |
| Dependabot security updates | ✅ **فعال شد** | — |
| محدودکردن اکشن‌های مجاز | ✅ **فعال شد** | فقط اکشن‌های متعلق به خود GitHub |
| اجبار پین اکشن به SHA | ✅ **فعال شد** | `sha_pinning_required: true` |
| مجوز پیش‌فرض `GITHUB_TOKEN` | ✅ فقط خواندن | `default_workflow_permissions: read` |

سه ردیف آخر مهم‌اند چون **سمت سرور** اجرا می‌شوند و با `--no-verify` یا با
Push از دستگاهی که هوک ندارد قابل دور زدن نیستند:

- `sha_pinning_required` باعث می‌شود Workflow با اکشن پین‌نشده اصلاً اجرا
  نشود. یعنی حتی اگر کسی `actions/checkout@v4` را دوباره اضافه کند، CI
  شکست می‌خورد و کسی متوجه می‌شود.
- فهرست مجاز به «اکشن‌های خود GitHub» محدود شده. افزودن یک اکشن شخص ثالث
  نیازمند تصمیم صریح و تغییر تنظیمات است، نه یک خط در YAML.
- توکن CI فقط خواندن دارد، پس یک Workflow ربوده‌شده نمی‌تواند روی مخزن
  بنویسد.

**جایگزین: هوک محلی `ops/hooks/pre-push`.**

این هوک پیش از اینکه چیزی از دستگاه خارج شود، سه کار می‌کند:
۱. جست‌وجوی الگوی راز (توکن GitHub، کلید خصوصی، کلید AWS، انتساب رمز)
۲. رد فایل‌های ممنوع (`.env`، `*.pem`، `*.key`، `id_rsa`، دامپ دیتابیس)
۳. اجرای کامل تست‌های مالی — Push با تست شکسته انجام نمی‌شود

از نظر امنیتی این **از Push Protection سمت سرور بهتر است**: راز اصلاً از
دستگاه خارج نمی‌شود، در حالی که Push Protection آن را پس از انتقال می‌گیرد.
از نظر انضباطی ضعیف‌تر است، چون با `--no-verify` قابل دور زدن است و اگر
کلون تازه بگیرید باید دوباره نصب شود:

```bash
ops/install-hooks.sh
```

اگر روزی خواستید محافظت واقعاً اجباری و غیرقابل دور زدن باشد، ارتقا به
**GitHub Pro** ارزان‌ترین راه است. تا آن موقع، هوک + CI کافی است.

### شکاف باقی‌مانده — صریح بگوییم

بدون Ruleset، **هیچ‌چیز سمت سرور مانع Push مستقیم روی `main` با تست شکسته
نمی‌شود.** CI بعد از Push اجرا می‌شود و شکست را نشان می‌دهد، ولی کد
تا آن موقع روی `main` نشسته است. تنها دروازه پیش از Push، هوک محلی است و
هوک روی **هر کلون جدید باید دوباره نصب شود**:

```bash
ops/install-hooks.sh
```

اگر روزی نفر دومی به پروژه اضافه شد، این دیگر کافی نیست و Pro لازم می‌شود.

### وابستگی‌ها

اکشن‌ها به SHA کامل پین شده‌اند. پین بدون نگهداری خودش به بدهی امنیتی
تبدیل می‌شود، چون نسخه قفل‌شده وصله‌های بعدی را نمی‌گیرد.
`.github/dependabot.yml` هفتگی SHAها را بررسی و از مسیر PR به‌روز می‌کند —
که یعنی هر به‌روزرسانی از تست‌های مالی رد می‌شود.

ورودی `npm` عمداً هنوز در آن فایل نیست؛ هم‌زمان با ساخت `apps/` اضافه شود.
