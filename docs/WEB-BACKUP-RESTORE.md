# پشتیبان‌گیری و بازیابی از وب

رابط: تنظیمات ← پشتیبان‌گیری و بازیابی. مجوزهای `backup.view`، `backup.create`،
`backup.download` و `backup.restore` مستقل‌اند؛ دامنهٔ همهٔ شعب، نشست انسانی کامل
و برای بازیابی، رمز مجدد و TOTP یا کد بازیابی یک‌بارمصرف لازم است.

این پیاده‌سازی تا نصب سرویس مستقل، صریحاً «متصل نشده» نمایش می‌دهد. اضافه‌شدن کد
یا موفقیت آزمون محلی به معنای نصب یا تأیید بازیابی دیتابیس عملیاتی نیست.

## مرز دسترسی

API عمومی فقط سوکت یونیکس و کلید کانال را دارد. سرویس مدیریتی با حساب مستقل
`labelmod-backup` اجرا می‌شود؛ خودش دوباره نشست و مجوز را بررسی می‌کند. اعتبارنامهٔ
مالک دیتابیس، کلید امضای بکاپ و فضای بکاپ به API، Worker و مرورگر داده نمی‌شوند.
هیچ مسیر، نام دیتابیس، SQL یا فرمانی از درخواست HTTP اجرا نمی‌شود.

فقط دامپ سفارشی تولیدشده توسط همین نصب با امضای HMAC و SHA-256 پذیرفته می‌شود.
آپلود دلخواه وجود ندارد. زمان ثبت‌شده از snapshot مشترک با pg_dump می‌آید.
نسخهٔ پستگرس و هش مرتب‌شدهٔ تمام نام/چک‌سام مهاجرت‌ها باید با اصلی یکسان باشند.
بکاپ قدیمیِ دارای اسکیما متفاوت ابتدا نیازمند تمرین مهاجرت مستقل است.

## ترتیب بازیابی

1. تطبیق شناسه و زمان صریحاً تأییدشده، امضا، اندازه و هش فایل.
2. ساخت دیتابیس تازه؛ اجرای pg_restore با `--exit-on-error --single-transaction`.
3. تطبیق مهاجرت‌ها، توازن دفتر، موجودی غیرمنفی، تطبیق انبار و دفتر، اشخاص، چک و زنجیرهٔ حسابرسی.
4. باطل‌کردن نشست‌ها، بلیت‌های ورود و کلیدهای ماشینی نسخهٔ بازیابی‌شده؛ غیرفعال نگه‌داشتن
   `Bardia` و `recovery_admin` بدون ایجاد هیچ‌یک.
5. توقف API، Worker و Scheduler، تأیید توقف، ساخت بکاپ تازهٔ بازگشت و کنترل هش آن.
   رمز، عوامل دوم و مجوزهای جاری برای کاربرانی که همان شناسه و نام کاربری را در بکاپ دارند
   حفظ می‌شوند؛ حساب ناشناخته/تغییرنام‌یافته فعال نمی‌شود و دستگاه‌ها نیازمند تأیید دوباره‌اند.
   مدیر درخواست‌کننده باید در نسخهٔ مقصد نیز دسترسی معتبر داشته باشد. بازیابی مالی، رمزها
   یا کلیدهای عامل دوم لغوشده را دوباره معتبر نمی‌کند.
6. جلوگیری از اتصال به دو دیتابیس، قطع اتصال‌های مانده، تغییر نام‌ها در یک تراکنش.
   دیتابیس قبلی حفظ می‌شود؛ هویت OID هر دو قبل از تغییر ثبت و بررسی می‌شود.
7. کنترل مالی اصلی، سپس شروع API. Worker و Scheduler و کلیدهای ماشینی برای جلوگیری
   از بازپخش پیام‌ها/سفارشهای قدیمی، تا بررسی مدیر اتصال‌ها متوقف می‌مانند.

همهٔ نویسنده‌های این استقرار باید همین سه سرویس باشند؛ نویسندهٔ بیرونی یا اپراتور
SQL هم‌زمان باید پیش از عملیات متوقف شود. این شرط باید در پذیرش استقرار بررسی شود.
پوشهٔ بکاپ شامل دادهٔ حساس است و باید روی دیسک رمزگذاری‌شده، با دسترسی محدود و نسخهٔ
جدا از میزبان نگه‌داری شود. حذف یا نگهداری خودکار نسخه‌های قبلی در این انتشار نداریم.

## استقرار میزبان

فایل‌های زیر نمونهٔ اجرایی برای استقرار ثابت `/srv/labelmod/app` هستند؛ پیش از نصب
روی میزبان واقعی، کاربر، گروه، مسیر Node و ابزارهای پستگرس و نام سرویس‌ها را تطبیق دهید:

- `ops/deploy/labelmod-backup.service`
- `ops/deploy/labelmod-backup.sudoers` (اعتبارسنجی و نصب با `visudo`)
- `ops/backup-writers.sh` به `/usr/local/sbin/labelmod-backup-writers` با مالک root و حالت 0755
- `ops/deploy/backup-writer-hook.sh` به `/usr/local/libexec/labelmod-backup-writer-hook` با مالک root و حالت 0755
- `docker-compose.backup.yml` همراه Compose تولیدی؛ پستگرس فقط روی loopback میزبان 55432 منتشر می‌شود.

سرویس مدیریتی نباید به مخزن کد، Compose، `.env` برنامه، helperهای root یا sudoers
دسترسی نوشتن داشته باشد. `labelmod-backup-control` پیش از شروع unit با مالک root و
حالت 0700 ساخته شود. کلید کانال API با کلید امضا متفاوت و هرکدام حداقل ۳۲ بایت تصادفی‌اند.
`BACKUP_SOCKET_GID` باید گروه مشترک سوکت باشد؛ API فقط امکان اتصال دارد.

فایل `/etc/labelmod-backup.env` فقط برای root و حساب سرویس قابل‌خواندن است:

```text
OPS_DATABASE_URL=postgresql://OWNER:ENCODED_PASSWORD@127.0.0.1:55432/labelmod
OPS_BACKUP_DIR=/var/lib/labelmod-backup
OPS_INSTANCE=labelmod-production
OPS_SIGNING_KEY=<64 hex characters, independent signing key>
OPS_RPC_TOKEN=<64 hex characters, same as API BACKUP_MANAGER_TOKEN>
OPS_SOCKET=/run/labelmod-backup/manager.sock
OPS_PG_BIN=/usr/bin
OPS_WRITER_HOOK=/usr/local/libexec/labelmod-backup-writer-hook
```

شروع مجدد سرویس، عملیات ناقص را پنهان یا دوباره اجرا نمی‌کند. وضعیت و قفل بیرون
دیتابیس باقی می‌مانند و صفحه پس از ورود دوباره، آن‌ها را نشان می‌دهد.

## قطع فرایند و بازگشت

در شکست پیش از شروع نویسنده‌های تازه، موتور با اثبات OIDها به دیتابیس قبلی برمی‌گردد.
اگر شروع نویسنده‌ها آغاز شده باشد، بازگشت خودکار ممنوع است: ممکن است فروش تازه ثبت
شده باشد. وضعیت `manual_recovery` و قفل باقی می‌مانند؛ مدیر باید دو نسخه را مقایسه کند.

برای توقف فرایند در مراحل قبل از `resuming`، پس از توقف unit و بررسی PID صاحب قفل،
CLI زیر با محیط همان سرویس قابل استفاده است:

```sh
node --experimental-strip-types apps/api/src/cli/backup-manager.ts --recover <job-uuid>
```

این CLI از HTTP قابل دسترسی نیست، وجود فرایند صاحب قفل را رد می‌کند، نام‌ها را
از شناسهٔ ثبت‌شده می‌سازد و فقط OIDهای همان عملیات را می‌پذیرد. حذف فایل قفل به‌تنهایی
راه ادامه نیست؛ وضعیت ناقص در تاریخچه نیز مانع شروع عملیات تازه است.

اگر فقط ساخت بکاپ قطع شده و هیچ بازیابی ناقصی در تاریخچه نیست، پس از توقف سرویس
می‌توان `--recover-backup-lock` را به همان CLI داد. ابزار فقط قفلِ فرایند مرده را
آزاد می‌کند؛ فرایند زنده، PID نامعتبر و وجود بازیابی ناقص را رد می‌کند و دیتابیس را تغییر نمی‌دهد.

پس از بازیابی موفق، مدیر باید صف‌های پیامک/اعلان و Push، کلیدهای اتصال و سفارش‌های
ثبت‌شده بیرون حسابداری پس از زمان بکاپ را تطبیق دهد، سپس Worker و Scheduler و کلیدهای
لازم را صریحاً فعال کند. این مرحله جای پذیرش مسئول حسابداری یا تمرین روی میزبان دیگر را نمی‌گیرد.
