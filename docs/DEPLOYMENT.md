# راه‌اندازی روی سرور

راهنمای گام‌به‌گام استقرار تولیدی. فرض: یک سرور لینوکسی (Ubuntu 22.04 یا
بالاتر)، یک دامنه، و دسترسی root.

> **قاعده حاکم همان است:** این سیستم پول یک کسب‌وکار واقعی را نگه
> می‌دارد. هیچ گامی را «فعلاً رد می‌کنم، بعداً درستش می‌کنم» نگذارید —
> مخصوصاً بکاپ و تست Restore.

---

## ۰. چه چیزی بالا می‌آید

پنج سرویس، و نه بیشتر (ADR-001):

| سرویس | کار | پورت روی میزبان |
| --- | --- | --- |
| `db` | PostgreSQL 16 | **هیچ** — فقط شبکه داخلی |
| `api` | Fastify، منطق مالی | **هیچ** — فقط از Caddy |
| `worker` | صف پیام: پیامک فاکتور، هشدار سررسید چک | — |
| `caddy` | TLS خودکار + سرو رابط کاربری + Reverse Proxy روی `/api` | ۸۰، ۴۴۳ |
| `scheduler` | بستن شبانه دوره فروش سایت، بکاپ | — |

**`worker` همان ایمیج `api` است با دستور دیگر** (ADR-001: «Worker:
همان کدبیس»). فرآیندش جداست چون ارسال پیامک ثانیه‌ها طول می‌کشد و
نباید در همان Event Loopی بنشیند که فاکتور صندوق را جواب می‌دهد.

**چرا پستگرس و API هیچ پورتی منتشر نمی‌کنند:** کوکی نشست در تولید
`Secure` است. اگر API از راه HTTP لخت هم قابل دسترس باشد، همان کوکی
روی یک مسیر رمزنشده می‌رود. تنها راه ورود به سیستم، Caddy است.

**چرا یک دامنه برای هر دو:** کوکی نشست `SameSite=Strict` است و رابط
کاربری `/api` را نسبی صدا می‌زند. UI و API روی دو دامنه یعنی هر درخواست
بین‌سایتی می‌شود، کوکی فرستاده نمی‌شود، و ورود بی‌هیچ پیام مفیدی کار
نمی‌کند.

## ۱. پیش‌نیاز روی سرور

```bash
# Docker Engine + Compose plugin
curl -fsSL https://get.docker.com | sh

# ساعت سرور — لاگ و زمان‌بند شبانه از این می‌خوانند.
# ⚠️ «امروز» در منطق مالی از تنظیم platform.timezone می‌آید، نه از اینجا.
timedatectl set-timezone Asia/Tehran
```

**DNS:** رکورد `A` (و در صورت داشتن IPv6، `AAAA`) دامنه باید به IP همین
سرور اشاره کند **پیش از** اولین اجرا. Let's Encrypt دامنه‌ای را که به
سرور نرسد تأیید نمی‌کند و Caddy در حلقه تلاش می‌ماند.

**فایروال:** فقط ۸۰، ۴۴۳ (TCP و UDP — برای HTTP/3) و پورت SSH.

```bash
ufw allow 22/tcp && ufw allow 80/tcp && ufw allow 443/tcp && ufw allow 443/udp && ufw enable
```

## ۲. گرفتن کد و پر کردن `.env`

```bash
mkdir -p /srv && cd /srv
git clone https://github.com/AliJ021/labelmod-core.git labelmod
cd labelmod

cp .env.example .env
chmod 600 .env          # بند ۸ SECURITY.md
```

حداقل این سه را عوض کنید:

```dotenv
DB_PASSWORD=<خروجی: openssl rand -base64 24 | tr -dc 'A-Za-z0-9'>
SITE_ADDRESS=shop.example.com
ACME_EMAIL=you@example.com
```

⚠️ **رمز پایگاه داده فقط حروف و رقم.** این مقدار داخل یک URL می‌نشیند؛
کاراکترهایی مثل `@` یا `:` یا `/` رشته اتصال را می‌شکنند و خطایش گمراه‌کننده
است.

## ۳. بالا آوردن

```bash
ops/deploy.sh up          # Build و اجرا
ops/deploy.sh migrate     # ساخت اسکیما
ops/deploy.sh seed        # کدینگ حساب، قواعد ثبت، تنظیمات، داده مرجع
ops/deploy.sh status
```

`up` را می‌شود هر بار بعد از `git pull` دوباره زد؛ فقط چیزی که عوض شده
دوباره ساخته می‌شود.

`migrate` و `seed` هر دو Idempotent‌اند: اجرای دوباره‌شان مقدار
تأییدشده حسابدار را به پیش‌فرض برنمی‌گرداند.

**بعد از هر مهاجرتی که حساب یا قاعده ثبت تازه لازم دارد، `seed` را
دوباره بزنید.**

### اولین گواهی

Caddy خودش از Let's Encrypt گواهی می‌گیرد؛ چند ثانیه تا چند دقیقه طول
می‌کشد. پیگیری:

```bash
ops/deploy.sh logs caddy
```

اگر خطای `could not get certificate` دیدید، تقریباً همیشه یکی از این
دوتاست: DNS هنوز به این سرور اشاره نمی‌کند، یا پورت ۸۰ بسته است.

⚠️ **حجم گواهی‌ها در `caddy_data` است.** آن Volume را پاک نکنید؛ صدور
دوباره سهمیه Let's Encrypt را می‌سوزاند.

## ۴. ساخت اولین مدیر

**`seed` هیچ حساب انسانی نمی‌سازد** — و عمداً. یک مدیر با رمز پیش‌فرضِ
کامیت‌شده یعنی رمزی که در مخزن نشسته، روی هر استقراری یکی است، و دقیقاً
همان چیزی است که اولین سطر فهرست کنترل بند ۸ SECURITY.md ممنوع می‌کند.

پس اولین حساب از خط فرمان ساخته می‌شود:

```bash
ops/deploy.sh user --username ali --name 'علی جوادی' --role admin --branch MAIN
```

```
✓ کاربر ساخته شد
  نام کاربری : ali
  نقش‌ها     : admin

  رمز عبور   : TXybpkz2hwmnxKBtocK6bHqw
```

رمز **ساخته می‌شود، پرسیده نمی‌شود**: ۲۴ کاراکتر از مولد امن، بدون
کاراکترهای مبهم (`O`/`0`، `l`/`1`). یک بار چاپ می‌شود و از آن به بعد
فقط هش Argon2id می‌ماند — قابل خواندن نیست، حتی از دیتابیس.

همان لحظه در یک مدیر رمز امن ذخیره‌اش کنید، وارد `https://<دامنه>` شوید
و عوضش کنید.

نقش‌های موجود: `admin` · `accountant` · `supervisor` · `cashier` ·
`warehouse` · `marketing`. چندتایی با کاما: `--role admin,accountant`.

⚠️ کاربر «سیستم» (`00000000-…-f1`) عمداً نه رمز دارد نه PIN و غیرفعال
است. آن را فعال نکنید — فقط یک نام برای سندی است که آدمی پشتش نیست.

⚠️ **PIN از این مسیر ست نمی‌شود.** PIN فقط قفل نشستِ موجود را باز
می‌کند و روی دستگاه تأییدشده معنا دارد (بند ۱ SECURITY.md).

## ۵. آنچه خودکار اجرا می‌شود

سرویس `scheduler` بدون cron کار می‌کند: هر ساعت بیدار می‌شود و اگر کار
امروز انجام نشده باشد اجرایش می‌کند.

| کار | ساعت پیش‌فرض | تنظیم |
| --- | --- | --- |
| بستن دوره ثبت فروش سایت | ۳ بامداد | `CLOSE_HOUR` در `.env` |
| بکاپ `pg_dump` | ۴ بامداد | `BACKUP_HOUR` در `.env` |

**بستن دوره موجودی را دست نمی‌زند.** کالا همان لحظه فروش از انبار خارج
شده؛ آنچه اینجا بسته می‌شود فقط سند حسابداری درآمد و بهای تمام‌شده است.

نشانه انجام‌شدن در یک Volume می‌نشیند، نه در حافظه — پس Restart ظرف
باعث اجرای دوباره در همان روز نمی‌شود.

سرویس `worker` جدا از این است و **حلقه‌ای** کار می‌کند، نه ساعتی: هر
چند ثانیه صف را می‌بیند.

| کار | هرچند وقت | تنظیم |
| --- | --- | --- |
| پیامک فاکتور به مشتری | با هر فاکتور نهایی‌شده | `notify.invoice_sms` |
| هشدار سررسید چک | روزی یک بار برای هر چک | `notify.cheque_due_sms` |

⚠️ **پیش‌فرض همه‌شان خاموش است، و سرویس‌دهنده پیامک `log`.** یعنی
پیام‌ها ساخته و بسته می‌شوند ولی هیچ پیامکی واقعاً نمی‌رود و متنش در
`ops/deploy.sh logs worker` دیده می‌شود. برای ارسال واقعی:

۱. `SMS_API_KEY` را در `.env` بگذارید و `ops/deploy.sh up` بزنید
۲. در صفحه تنظیمات، گروه «پیامک و اطلاع‌رسانی»:
   سرویس‌دهنده، شماره فرستنده، «ارسال پیامک فعال باشد»
۳. `platform.public_url` را پر کنید — بدون آن لینک فاکتور ساخته
   نمی‌شود و پیامک فاکتور در صف می‌ماند

کنترل روزانه:

```bash
ops/deploy.sh status      # درآمد ثبت‌نشده + پیام‌های نرفته + چک سررسیدشده
```

دو چیز باید **خالی** باشند:

- `sales.unposted_revenue` — اگر نبود، درآمدی به دفتر نرفته.
- `platform.outbox_dead` — اگر نبود، پیامی هست که پس از سقف تلاش هرگز
  نرفت. ستون `last_error` می‌گوید چرا.

## ۶. بکاپ — جایی که بیشترین اشتباه رخ می‌دهد

دامپ خودکار در `${BACKUP_DIR}` (پیش‌فرض `./backup`) می‌نشیند و ۳۰ روز
نگه داشته می‌شود.

**این هنوز بکاپ نیست.** بند ۴ SECURITY.md دو چیز می‌خواهد که ظرف
نمی‌تواند بدهد:

**۱. رمزنگاری و خروج از سرور.** یک کار روزانه روی میزبان:

```bash
# /etc/cron.d/labelmod-offsite
30 4 * * * root age -r <کلید-عمومی> \
  /srv/labelmod/backup/$(date +\%Y\%m\%d)*.dump \
  -o /tmp/labelmod-$(date +\%Y\%m\%d).age && \
  rclone copy /tmp/labelmod-*.age remote:labelmod/ && rm -f /tmp/labelmod-*.age
```

کلید خصوصی **خارج از همین سرور و خارج از مخزن** نگه داشته شود. بکاپی که
کلیدش کنار خودش باشد، در حادثه‌ای که برایش ساخته شده بی‌فایده است.

**۲. تمرین Restore ماهانه — با یک دستور.**

```bash
ops/restore-drill.sh                 # جدیدترین دامپ در $BACKUP_DIR
ops/restore-drill.sh backup/x.dump   # یک فایل مشخص
```

اسکریپت یک دیتابیس **یک‌بارمصرف** می‌سازد، دامپ را در آن برمی‌گرداند،
یازده ادعا رویش می‌راند و در پایان دیتابیس را می‌اندازد. تنها نوشتنش روی
دیتابیس عملیاتی، ثبت خودِ تمرین است.

| ادعا | چرا |
| --- | --- |
| جدول‌های مالی برگشته‌اند | دامپ فقط-داده اینجا رد می‌شود |
| کدینگ حساب، قواعد ثبت، تنظیمات | بدون این‌ها هیچ سندی ساختنی نیست |
| هیچ سند نامتوازنی نیست | همان ادعای CI، روی داده بازیابی‌شده |
| هیچ موجودی منفی‌ای نیست | همان |
| زنجیره حسابرسی **حلقه‌به‌حلقه** | دامپی که وسطش افتاده، همین‌جا لو می‌رود |
| توابع مالی برگشته‌اند | منطق مالی در دیتابیس است؛ بکاپ بدون آن نصفه است |

«فایل باز شد» کافی نیست: یک دامپ می‌تواند بی‌خطا بازیابی شود و باز هم
بی‌فایده باشد.

**زنگ خطر:** `ops/deploy.sh status` وضعیت مهلت را نشان می‌دهد.

```
never     هرگز آزموده نشده — بدترین حالت
overdue   از `backup.restore_drill_days` گذشته
ok        در مهلت
```

⚠️ **تمرین ناموفق زنگ را خاموش نمی‌کند.** تمرینی که شکست خورده ثابت
کرده بکاپ سالم **نیست**؛ شمردنش به‌عنوان «آخرین تمرین» یعنی هشدار را با
همان چیزی خاموش کنیم که باید بلندش کند. `db/test/restore-drill.sql`
همین را قفل کرده.

سابقه تمرین‌ها در `platform.restore_drill` می‌نشیند و **تغییرناپذیر**
است — تاریخچه‌ای که بشود عقب بردش، تاریخچه نیست.

برای cron شبانه یا هفتگی:

```cron
0 4 * * 0  cd /srv/labelmod && ops/restore-drill.sh >> /var/log/labelmod-drill.log 2>&1
```

اسکریپت روی شکست کد خروج غیرصفر می‌دهد، پس cron می‌تواند ایمیل بزند.

**بکاپی که Restore آن تست نشده، بکاپ نیست — یک فایل است با یک فرض.**

## ۷. هدرهای امنیتی و اسکنر بارکد

Caddy این‌ها را روی هر پاسخ می‌گذارد (بند ۲ و ۶ SECURITY.md):

```
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Content-Type-Options: nosniff
Referrer-Policy: same-origin
Cross-Origin-Opener-Policy: same-origin
Permissions-Policy: camera=(self), microphone=(), geolocation=(), payment=(), usb=()
Content-Security-Policy: default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; …
```

### ⚠️ `wasm-unsafe-eval` — دست نزنید

اسکنر بارکد موبایل روی هر مرورگری که `BarcodeDetector` بومی ندارد —
**از جمله آیفون** — از WebAssembly استفاده می‌کند. فایل WASM محلی سرو
می‌شود، ولی محلی‌بودن جای **اجازه اجرا** را نمی‌گیرد.

بدون این کلیدواژه دوربین باز می‌شود، تصویر می‌آید، و هیچ بارکدی خوانده
نمی‌شود — خرابی‌ای که هیچ خطایی نمی‌دهد و ماه‌ها کشف نشده می‌ماند.

`apps/web/test/csp.test.ts` این را در CI قفل کرده. اگر آن تست قرمز شد،
یعنی یک دفاع یا یک قابلیت شکسته — نه اینکه تست سخت‌گیر است.

### دوربین فقط روی HTTPS

`getUserMedia` روی `http://` (جز `localhost`) اصلاً اجازه کار ندارد.
یعنی **اسکن با موبایل تا وقتی TLS بالا نیامده امتحان‌پذیر نیست.**

### CSP صفحه چاپ برچسب بازنویسی نمی‌شود

صفحه برچسب CSP سخت‌گیرتر خودش را می‌فرستد (`script-src` کاملاً بسته).
Caddy روی `/api/*` هدر را با `?` می‌گذارد — یعنی «فقط اگر پاسخ خودش
نگذاشته باشد». آزموده شد، نه فرض.

## ۸. به‌روزرسانی

```bash
cd /srv/labelmod
git pull
ops/deploy.sh up
ops/deploy.sh migrate     # اگر مهاجرت تازه آمده

#### ⚠️ اولین ارتقا پس از آمدنِ دفتر مهاجرت

تا پیش از این، `migrate` هر فایل را از ۰۰۱ دوباره اجرا می‌کرد و روی
دیتابیسی که یک بار مهاجرت شده بود سرِ اولین فایل می‌شکست:

```
ERROR:  schema "platform" already exists
```

یعنی **هیچ مهاجرت تازه‌ای به سرور نمی‌رسید**. حالا یک دفتر ساده در
`public.schema_migration` هر فایلِ اجراشده را با هش محتوایش نگه می‌دارد.

سروری که پیش از این تغییر بالا آمده، دفتر ندارد. `migrate` این را
تشخیص می‌دهد و می‌ایستد. یک بار وضعیت را ثبت کنید:

```bash
# شماره آخرین مهاجرتی که واقعاً روی این سرور اجرا شده
ops/deploy.sh baseline 031
ops/deploy.sh migrate            # حالا فقط ۰۳۲ به بعد اجرا می‌شوند
```

⚠️ **شماره را حدس نزنید.** اگر عدد بزرگ‌تر از واقعیت بدهید،
مهاجرت‌هایی که اجرا نشده‌اند «اجراشده» ثبت می‌شوند و **هرگز اجرا
نمی‌شوند** — بدون هیچ خطایی؛ فقط تابعی که وجود ندارد و اولین
فراخوانی‌اش می‌شکند. عدد را از نسخه‌ای که آخرین بار Deploy شده
بردارید:

```bash
git log --oneline -1        # روی همان تگ/کامیت
ls db/migrations | tail -1  # در همان نسخه
```

اگر مطمئن نیستید، اول بکاپ بگیرید و اسکیما را مقایسه کنید.

`migrate` دوباره‌اجراشدن یک مهاجرت را هم می‌گیرد: اگر فایلی **پس از
اجرا** ویرایش شود، هشش عوض می‌شود و مهاجرت با پیام صریح می‌ایستد —
همان قاعده «مهاجرت موجود ویرایش نمی‌شود»، این بار اجباری.
ops/deploy.sh seed        # اگر حساب یا قاعده ثبت تازه آمده
```

هنگام Restart سرویس `api`، Caddy تا ۵ ثانیه تلاش دوباره می‌کند
(`lb_try_duration`) — پس Deploy برای صندوق‌دار به‌شکل یک مکث دیده
می‌شود، نه یک صفحه خطا.

## ۹. عیب‌یابی

| نشانه | علت رایج |
| --- | --- |
| `could not get certificate` | DNS به این سرور اشاره نمی‌کند، یا پورت ۸۰ بسته است |
| ورود ۴۰۳ با `csrf_failed` | کوکی CSRF از بین رفته — یک بار Refresh کامل صفحه |
| هر درخواست ۴۰۱ | کوکی نشست نمی‌رسد: UI و API روی یک دامنه نیستند |
| دوربین باز می‌شود ولی بارکد نمی‌خواند | `wasm-unsafe-eval` از CSP افتاده |
| دوربین اصلاً باز نمی‌شود | صفحه روی HTTP است، نه HTTPS |
| `DB_PASSWORD لازم است` | `.env` نیست یا خوانده نشده |
| API بالا نمی‌آید، لاگ: «پیکربندی نامعتبر» | یک متغیر محیطی لازم غایب است — پیام فارسی نامش را می‌گوید |
| فاکتور امروز در دفتر نیست | طبیعی است تا بسته‌شدن دوره؛ `ops/deploy.sh status` را ببینید |

لاگ‌ها:

```bash
ops/deploy.sh logs api
ops/deploy.sh logs caddy
ops/deploy.sh logs scheduler
```

هر پاسخ خطای API یک `correlationId` دارد که در لاگ ساختاریافته هم هست —
از همان بگردید.

## ۱۱. نقش برنامه بدون حق نوشتن مستقیم

بند ۳ `docs/SECURITY.md` می‌گوید نقش اپلیکیشن نباید DDL بزند و نباید روی
جدول‌های تغییرناپذیر بنویسد. **تا شهریور ۱۴۰۵ این فقط یک جمله بود** — نه
نقشی ساخته می‌شد، نه `REVOKE`ای اجرا. `docker-compose.yml` یک کاربر
می‌سازد که **مالک** دیتابیس است و همه‌چیز را می‌تواند، از جمله
`UPDATE inventory.stock_balance SET on_hand = 999`.

```bash
# با DATABASE_URL مالک — همان که مهاجرت با آن اجرا می‌شود
APP_PASSWORD='یک رمز تصادفی بلند' ops/db-roles.sh
```

اسکریپت Idempotent است: اجرای دوباره فقط GRANT/REVOKE را تازه می‌کند و
رمز را تنها وقتی عوض می‌کند که `APP_PASSWORD` داده شده باشد.

سپس در `.env`، متغیر اتصال **برنامه** (و فقط برنامه) به نقش تازه عوض شود.
مهاجرت‌ها با همان نقش مالک قبلی اجرا می‌شوند:

```
DATABASE_URL=postgres://labelmod_app:<رمز>@db:5432/labelmod   # api و worker
MIGRATION_DATABASE_URL=postgres://labelmod:<رمز>@db:5432/labelmod
```

⚠️ **تا این متغیر عوض نشود، اجرای اسکریپت هیچ محدودیتی فعال نمی‌کند.**
نقش ساخته می‌شود و بی‌استفاده می‌ماند.

⚠️ **پس از هر مهاجرتی که جدول تازه بسازد**، اسکریپت را دوباره اجرا کنید.
`ALTER DEFAULT PRIVILEGES` بیشتر موارد را پوشش می‌دهد، ولی جدولی که پیش
از تنظیم آن ساخته شده باشد GRANT نمی‌گیرد.

⚠️ **بکاپ با نقش مالک گرفته می‌شود، نه با نقش برنامه.** `pg_dump` روی
`public.schema_migration` هم `LOCK TABLE` می‌زند و نقش برنامه آنجا حقی
ندارد. اگر `DATABASE_URL` را در `.env` عوض کنید و `ops/db.sh backup` هم
همان را بخواند، بکاپ شبانه با
«permission denied for table schema_migration» می‌ایستد. `ops/deploy.sh`
از متغیر مالک استفاده می‌کند؛ هر cron دستی هم باید همان را بگیرد.

### چه چیزی واقعاً بسته می‌شود

ده حمله که با نقش مالک همه‌شان موفق می‌شوند:

| حمله | با نقش برنامه |
|---|---|
| `UPDATE`/`DELETE`/`INSERT` روی `inventory.stock_movement` | رد |
| `UPDATE`/`DELETE` روی `platform.audit_log` | رد |
| `CREATE TABLE` در اسکیمای مالی | رد |
| **`UPDATE` مستقیم روی `inventory.stock_balance`** | رد |
| `INSERT`/`UPDATE` روی `inventory.cost_layer` | رد |
| `CREATE TABLE` در اسکیمای `public` | رد |
| `SELECT inventory.apply_movement(…)` | **کار می‌کند** |
| `SELECT inventory.revalue_to_cost(…)` | **کار می‌کند** |

دو سطر آخر مهم‌ترین‌اند: بی‌آن‌ها، قفل دروازه را هم بسته بود.

⚠️ سطر `public` هم یک نگهبان واقعی است، نه تشریفات: هر شش تابع
`SECURITY DEFINER` این پروژه `public` را در `search_path` پین‌شدهٔ خود
دارند (چون `pgcrypto` آنجاست). نقشی که بتواند در `public` شیء بسازد،
می‌تواند تابعی هم‌نام بگذارد که **به‌نام مالک** اجرا شود — یعنی دقیقاً
همان ارتقای دسترسی که پین‌کردن `search_path` قرار بود ببندد. پستگرس ۱۵
به بعد پیش‌فرض بسته‌اش کرده، ولی دیتابیسِ ارتقایافته از نسخهٔ قدیمی‌تر
هنوز بازش دارد.

### چرا این بار واقعاً سنجیده شد

تا امروز تنها چیزی که با نقش برنامه سنجیده می‌شد `db/test/db-roles.sh`
بود و آن فقط `apply_movement` را به‌عنوان «دروازه» می‌شناخت. بقیهٔ
مجموعه — ۱۲۴۵ ادعای SQL و ۶۵۴ ادعای API — با نقش **مالک** اجرا می‌شدند،
و مالک همه‌چیز را می‌تواند.

حالا کل مجموعهٔ یکپارچهٔ API یک بار با نقش محدود اجرا می‌شود:

```bash
LMC_TEST_DB_ROLE=app pnpm --filter @labelmod/api test
```

`test/helpers/disposable-db.ts` در این حالت پس از مهاجرت و Seed، همان
`ops/db-roles.sh` تولیدی را روی دیتابیس یک‌بارمصرف اجرا می‌کند و برنامه
را با نقش محدود وصل می‌کند — مهاجرت با مالک، برنامه با نقش محدود، دقیقاً
شکل تولید.

**اولین اجرا ۳۰ شکست داد** و دو ریشه داشت، هر دو در مسیر تولید:

| ریشه | اثر در تولید |
|---|---|
| `inventory.revalue_to_cost()` `SECURITY DEFINER` نبود | با `costing.method = last_purchase` (پیش‌فرض) **هیچ رسید خریدی ثبت نمی‌شد** |
| `inventory.post_stock_count()` `SELECT … FOR UPDATE` روی `stock_balance` دارد | هیچ انبارگردانی‌ای بسته نمی‌شد |

مهاجرت ۰۵۸ هر دو را بست. `SELECT … FOR UPDATE` در پستگرس حق **UPDATE**
می‌خواهد نه SELECT — و خطایش هیچ اشاره‌ای به `FOR UPDATE` ندارد.

و `db/test/write-gate.sql` این **کلاس** را بست، نه این دو مورد را:
کاتالوگ را می‌خواند و هر تابعی را که به سه جدول قفل‌شده بنویسد یا
قفلشان کند و `SECURITY DEFINER` نباشد، رد می‌کند.

⚠️ برای نقش **مالک** هیچ‌کدام بسته نیست و نباید باشد — مهاجرت با همان
نقش اجرا می‌شود. پس نماهای `inventory.balance_check` و
`inventory.ledger_check` هنوز لازم‌اند و `ops/deploy.sh status` نشانشان
می‌دهد.

## آنچه این استقرار عمداً ندارد

- **Redis، Kubernetes، Microservice** — ADR-001.
- **چند سرور یا Failover.** یک فروشگاه، یک سرور. اگر روزی لازم شد، یک
  ADR می‌خواهد نه یک فایل Compose.
- **فونت محلی.** `index.html` هنوز Vazirmatn را از Google Fonts می‌گیرد
  و CSP همان دو مبدأ را باز گذاشته. در قطعی اینترنت، صفحه با فونت
  سیستمی بالا می‌آید — کار می‌کند ولی زشت است. میزبانی محلی فونت یک
  تغییر جداست.
