## قواعد سخت

- Hex فقط در `tokens.css` (`design-system.test.ts` می‌سنجد)؛ مدت انیمیشن و اندازهٔ تکرارشونده هم از توکن. کم بود؟ توکن اضافه کن.
- پول فقط با `Money`؛ تاریخ فقط با `formatJalali`؛ وضعیت فقط با `StatusBadge`.
- `dir="ltr"` فقط از راه `Ltr`؛ خاصیت فیزیکی جهت‌دار ممنوع.
- هر عمل نهایی/مالی از `SafeAction` یا همان مراحل؛ نتیجهٔ نامعلوم هرگز «ارسال دوباره» ندارد.
- هیچ عدد، نمودار یا شمارندهٔ ساختگی کنار دادهٔ واقعی. داده نیست؟ بگو چرا.
- هیچ شرط دسترسی در کد: نمایش از `/auth/can`، دروازه در سرور.
- UI Kit همراه primitive تازه به‌روز می‌شود؛ آزمون واحد منطق خالص را، آزمون مرورگر چیدمان را.
- هیچ آزمونی حذف، Skip یا ضعیف نمی‌شود؛ ماتریس ۲۴ پروژهٔ مرورگر (با WebKit) کم نمی‌شود.

## نمونه — «برداشت و پاداش هر کاربر» (ساخته نمی‌شود؛ فقط آزمون قرارداد)

> ⚠️ **منسوخ برای دفتر برداشت واقعی.** ویژگی ساخته‌شده (مهاجرت ۰۸۴، تصمیم مالک ۱۴۰۵/۰۷/۱۰) فقط «مبلغ + دلیل» را ثبت می‌کند و **هیچ** سند، `post_entry`، اثر خزانه، کشو، انبار یا حقوق ندارد؛ اصلاح مدیر کل نسخهٔ تازه است، نه سند معکوس. جدول زیر فقط نمونهٔ پاسخ‌دادن به پرسش‌هاست، نه طرح آن ویژگی.

| پرسش | پاسخ |
|---|---|
| الگو | فهرست (برداشت‌ها) + جزئیات موجودیت (کاربر) + فرم (ثبت) |
| primitive | `DataTable`، `Money side`، `StatusBadge`، `Field`، `SafeAction` |
| ناوبری | «مالی و گزارش» → زیرزبانهٔ خزانه، نه مقصد اصلی تازه |
| مجوز | عملیات تازه در `permission_rule` (مثلاً `payout.create`/`payout.approve`)؛ تأیید جدا از ثبت‌کننده |
| حالت‌ها | خالی با `accent="ledger"`؛ بی‌مجوز با نام دسترسی؛ نامعلوم با بررسی وضعیت |
| موبایل | جدول `stack`؛ مبلغ هرگز نمی‌شکند |
| Bidi | شمارهٔ کارت/شبا در `Ltr` و فقط چهار رقم آخر |
| حسابرسی | خط زمانی: ثبت‌کننده، تأییدکننده، زمان، سند مرجع |
| حرکت | فقط کارکردی (Dialog) |
| آزمون | SQL برای سند و توازن؛ API با نقش مالک و محدود؛ مرورگر برای عمل ایمن و نامعلوم |
| بصری | تصویر مرجع فهرست و فرم در ۳۷۵/۱۴۴۰ |
| مالی | سند فقط از `ledger.post_entry()`؛ اصلاح با سند معکوس؛ `SafeAction` با `verify` خواندنی |
