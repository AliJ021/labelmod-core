# امکان‌سنجی چاپ مستقیم رسید از iPhone و Android روی MEVA TP-UNW در LAN (R01)

**وضعیت:** امکان‌سنجی؛ هیچ مسیری با چاپ فیزیکی پذیرفته نشده است. **تاریخ:** ۲۰۲۶/۱۰/۲۶ (اصلاح‌شده پس از بازبینی root همان روز: استثنای mixed content در LNA کروم، موتور جایگزین iOS در اتحادیهٔ اروپا، «نامعلوم» به‌جای «ندارد» برای API چاپگر، و دسترسی از راه VPN برای P6).

## خواستهٔ مالک

خواستهٔ مالک (ثبت از ۱۳ اکتبر) این است:
- رسید از **هر دو** iPhone و Android مستقیم روی MEVA TP-UNW چاپ شود و ارتباط با چاپگر از راه **LAN** باشد.
- **بی پنجره یا تب اضافه** چاپ شود.
- **بی PC یا bridge همیشه‌روشن** کار کند.

وضعیت فعلی: چاپگر با USB به Windows صندوق وصل است و مالک قصد دارد آن را روی LAN ببرد. این سند فقط امکان را می‌سنجد. پرسش دوباره دربارهٔ مدل، سیستم‌عامل یا نحوهٔ اتصال در کار نیست.

## آنچه دربارهٔ چاپگر مستند است و آنچه نیست

**سند رسمی نیست.** در جست‌وجوی ۲۶ اکتبر هیچ datasheet یا راهنمای برنامه‌نویسی رسمی MEVA برای TP-UNW پیدا نشد. همهٔ مشخصات پایین از صفحه‌های فروشندگان است و تأیید سازنده نیست:

| مورد | آنچه فروشندگان نوشته‌اند | میزان اطمینان |
|---|---|---|
| درگاه | USB، Ethernet (LAN)، Wi-Fi | چند فروشنده هم‌خوان‌اند ([source-computer](https://source-computer.com/product/meva-tp-unw-wifi-thermal-printer)، [mahamprint](https://mahamprint.com/products/---meva-tp-unw)) |
| فرمان | سازگار با ESC/POS؛ درایور Windows، Linux CUPS و OPOS | فقط یک فروشنده؛ نوشته نشده که ESC/POS روی LAN هم کار می‌کند |
| کاغذ | حرارتی ۸۰ میلی‌متر، ۲۰۳dpi (۵۷۶ نقطه در هر خط)، برش خودکار | چند فروشنده هم‌خوان‌اند ([digitalshop](https://digitalshop.ir/product/%D9%BE%D8%B1%DB%8C%D9%86%D8%AA%D8%B1-%D8%AD%D8%B1%D8%A7%D8%B1%D8%AA%DB%8C-%D9%85%DB%8C%D9%88%D8%A7-%D9%85%D8%AF%D9%84-tp-unw/)) |
| AirPrint / Mopria / IPP | **هیچ اشاره‌ای پیدا نشد** | ادعا نمی‌شود |
| API چاپ HTTP یا JavaScript (مانند Epson ePOS یا Star WebPRNT) | **هیچ اشاره‌ای پیدا نشد** | **نامعلوم** — پیدا نشدن در منابع دردسترس اثبات نبودن نیست؛ فقط خود دستگاه (صفحهٔ مدیریت، پورت‌های باز) یا سازنده روشنش می‌کند |

چند نکته از همین وضعیت نتیجه می‌شود:
- فرض کار این است که روی LAN احتمالاً پورت خام TCP (معمولاً ۹۱۰۰) با ESC/POS در دسترس است. این را **فقط خودِ دستگاه** ثابت می‌کند: برگهٔ self-test شبکه و یک ارسال آزمایشی از همان LAN.
- چاپ مستقیم متن فارسی با code page در ESC/POS قابل اتکا نیست. مسیر امن این است که رسید به‌شکل **تصویر raster** فرستاده شود (`GS v 0`). شکل‌دهی حروف فارسی را مرورگر یا سیستم‌عامل انجام می‌دهد و چاپگر فقط بیت‌مپ می‌گیرد.

## محدودیت‌های سکو، از منبع رسمی

- **iOS:** مرورگرهای iOS **بیرون از اتحادیهٔ اروپا** روی WebKit اجرا می‌شوند. در اتحادیهٔ اروپا، از iOS 17.4 و iPadOS 18، اپ مرورگر با entitlement مخصوص می‌تواند موتور جایگزین داشته باشد ([Apple: Alternative browser engines](https://developer.apple.com/support/alternative-browser-engines/)). پس «همهٔ مرورگرهای iOS WebKit‌اند» مطلق نیست؛ برای گوشی‌ای که بیرون از EU توزیع و استفاده می‌شود همچنان برقرار است. **WebUSB و Web Serial در Safari/WebKit پشتیبانی نمی‌شوند** ([caniuse Web Serial](https://caniuse.com/web-serial)، [caniuse WebUSB](https://caniuse.com/webusb)). فرمان `window.print()` در Safari برگهٔ چاپ سیستم را باز می‌کند و چاپ از راه AirPrint انجام می‌شود. صفحهٔ وب نمی‌تواند این برگه را رد کند.
- **Android Chrome:** فرمان `window.print()` به `PrintManager` چارچوب چاپ Android می‌رسد ([commit کرومیوم](https://chromium.googlesource.com/chromium/src.git/+/4c172eea8b6649f1c1c620d1daa20ce733cee9e1)). دیالوگ چاپ سیستم همیشه نشان داده می‌شود، و چاپگر فقط وقتی دیده می‌شود که یک print service plugin سازگار نصب باشد ([چارچوب چاپ Android](https://developer.android.com/training/printing/html-docs?hl=en)).
- **سوکت خام TCP از صفحهٔ وب ممکن نیست.** Direct Sockets (`TCPSocket`) فقط در **Isolated Web App** کار می‌کند، با manifest و permission policy صریح ([Chrome: Direct Sockets](https://developer.chrome.com/docs/iwa/direct-sockets)). صفحهٔ عادی HTTPS این API را ندارد. IWA روی iOS وجود ندارد و برای Android هم سندی دربارهٔ پشتیبانی‌اش پیدا نکردم.
- **درخواست از سایت عمومی به شبکهٔ محلی** در Chrome زیر Local Network Access (LNA) است: اجازهٔ کاربر می‌خواهد و برای iframe باید صریح اعلام شود ([Chrome: Local Network Access](https://developer.chrome.com/blog/local-network-access)). همان منبع می‌گوید درخواست محلیِ دارای این اجازه **از سنجش mixed content معاف است**، به شرط اینکه Chrome پیش از resolve بداند مقصد محلی است: نشانی IP خصوصی صریح (`192.168.x.x`)، نام `.local`، یا `fetch` با `targetAddressSpace: "local"`. پس جملهٔ پیشین «صفحهٔ HTTPS نمی‌تواند به `http://` چاپگر درخواست بفرستد» **نادرست بود**. طبق همان منبع، اعلان اجازه از Chrome 142 است. رفتار Safari/WebKit در این باره را منبعی نسنجیده‌ام و ادعا نمی‌کنم.
- **Epson ePOS SDK for JavaScript** نمونه‌ای از «چاپ مستقیم از مرورگر روی LAN» است. ولی فقط با چاپگرهای TM خودِ Epson کار می‌کند و API چاپ را خودِ چاپگر روی HTTP ارائه می‌دهد ([Epson ePOS SDK](https://download4.epson.biz/sec_pubs/pos/reference_en/technology/epson_epos_sdk.html)). برای MEVA چنین API **مستندی پیدا نشد**؛ وجود یا نبودش نامعلوم است.

جزئیات چند ستون:
- **P6:** «raw printer port روی اینترنت» ممنوع است و پیشنهاد نمی‌شود. اگر میزبان نهایی بیرون از فروشگاه باشد، دو راه هست: (الف) **VPN امن site-to-site** میان میزبان و شبکهٔ فروشگاه (مثلاً WireGuard یا IPsec روی روتری که امروز هست، اگر پشتیبانی کند)، که پورت چاپگر را عمومی نمی‌کند و PC همیشه‌روشن نمی‌خواهد؛ یا (ب) عامل محلی روی LAN، که همان bridge همیشه‌روشن است و شرط مالک ردش می‌کند. برای (الف) سخت‌افزار تازه فرض نمی‌شود، ولی پشتیبانی روتر فعلی، نشانی‌دهی (همپوشانی نشدن زیرشبکه‌ها) و فایروال (فقط میزبان → `printer:9100`) هنوز سنجیده نشده‌اند. چاپ هم به برقرار بودن تونل و اینترنت فروشگاه وابسته است.
- **P7 روی iOS:** iOS یک بار اجازهٔ **Local Network** را از کاربر می‌گیرد. توزیع اپ هم حساب Apple Developer و TestFlight، App Store یا ad hoc لازم دارد.
- **P7 روی Android:** نصب APK مستقیم ممکن است.

## نتیجه: blocker صریح

**R01 با همان شرط‌ها، یعنی فقط مرورگر روی iPhone و Android، بی هیچ دیالوگ، بی واسط و با MEVA فعلی، با شواهد موجود اثبات‌پذیر نیست — و ناممکن‌بودنش هم ادعا نمی‌شود.**

آنچه از منابع رسمی ثابت است:
- مرورگرهای موبایل سوکت خام ندارند (Direct Sockets فقط IWA).
- `window.print()` (AirPrint و چاپ Android) همیشه دیالوگ سیستم نشان می‌دهد.

آنچه نامعلوم است و فقط با دستگاه یا آزمون روشن می‌شود:
- آیا MEVA TP-UNW روی LAN API چاپ HTTP دارد؟ در منابع دردسترس پیدا نشد.
- اگر داشته باشد، P4 در Chrome اندروید با اجازهٔ LNA (معاف از mixed content برای IP صریح، `.local` یا `targetAddressSpace`) شدنی به نظر می‌رسد؛ روی iPhone بیرون از EU موتور WebKit است و رفتارش سنجیده نشده.

دامنه را پنهانی تغییر نمی‌دهم: شرط‌های هر سکو (انتقال، اجازه، امنیت) و پذیرش فیزیکی باز می‌مانند.

**تصمیم لازم از مالک — یکی از این گزینه‌ها:**

1. **P7، اپ بومی سبک:** اپ برنامهٔ موجود را در WebView نشان می‌دهد و پل چاپ دارد. رسید در اپ به raster ESC/POS تبدیل و مستقیم به `IP:9100` چاپگر فرستاده می‌شود.
   - این تنها گزینه‌ای است که همهٔ شرط‌ها را نگه می‌دارد.
   - برای iPhone حساب Apple Developer و روش توزیع (TestFlight، ad hoc یا App Store) لازم است. Android با APK ممکن است.
   - هزینه: یک کدبیس بومی تازه و نگهداری آن.
2. **P6، میزبان در LAN فروشگاه:** فقط اگر سرور نهایی در خود فروشگاه باشد. در آن صورت سرور مستقیم روی LAN چاپ می‌کند و هر گوشی فقط یک دکمه دارد.
   - شرط: میزبان و چاپگر در یک شبکه باشند. چاپ وقتی سرور یا شبکه قطع است ممکن نیست.
3. **پذیرش دیالوگ سیستم (P1/P2):** فقط اگر چاپگر AirPrint یا Mopria را واقعاً پشتیبانی کند، که باید روی دستگاه اثبات شود. این گزینه شرط «بی پنجره» را نقض می‌کند و فقط با موافقت صریح مالک قابل قبول است.
4. **P4، اگر دستگاه API چاپ HTTP داشت:** پیش از هر کد، صفحهٔ مدیریت و پورت‌های باز MEVA روی LAN بررسی شوند. اگر API واقعی بود، آزمون LNA در Chrome اندروید و Safari iPhone جدا انجام شود.
5. **P9، تعویض چاپگر:** خرید چاپگری با API چاپ وب. مشکل گواهی HTTPS خودِ چاپگر و اجازهٔ Local Network هنوز باید جداگانه حل و آزموده شود.

## پیش‌شرط سخت‌افزاری مشترک همهٔ گزینه‌ها جز P1/P2

این‌ها باید روی همان دستگاه انجام و ثبت شوند:

1. چاپگر روی LAN با **IP ثابت یا رزرو DHCP** باشد.
2. برگهٔ self-test شبکه چاپ شود و IP، پورت و پروتکل‌ها را نشان دهد.
3. از یک رایانه در **همان LAN** و فقط روی همان شبکهٔ داخلی، یک فرمان آزمایشی ESC/POS به پورت ۹۱۰۰ فرستاده و خروج کاغذ دیده شود. بی این شاهد، هیچ مسیری «اثبات‌شده» نامیده نمی‌شود.

## بخشی که بدون تصمیم و بدون دستگاه اجرا نمی‌شود

برای گزینه‌های ۱ و ۲ یک تکهٔ مشترک لازم است: رندر رسید روی canvas، تبدیل به raster تک‌رنگ ۵۷۶ نقطه‌ای و فرمان `GS v 0`. این تکه را می‌شود با آزمون واحدِ رفت‌وبرگشت (encode، سپس decode) نوشت.

ولی پیش از انتخاب گزینه و پیش از شاهد پورت ۹۱۰۰، ساختنش کد بی‌مصرف و ادعای بی‌پشتوانه است. پس **تا تصمیم مالک ساخته نمی‌شود** و در `REQUEST-TRACEABILITY.md` با معیار پذیرش ثبت است.

هیچ آزمون مرورگری جای چاپ واقعی را نمی‌گیرد. «دیالوگ بسته شد» هم یعنی «کاغذ چاپ شد» نیست.
