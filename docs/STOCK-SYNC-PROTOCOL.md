# پروتکل موجودی سایت — واترمارک و دفتر کسر محلی (مرحلهٔ ۱: صحت)

Core مرجع است. سایت عددی نشان می‌دهد که از عکس Core و کسرهای محلیِ هنوز تأییدنشده ساخته می‌شود.
این مرحله فقط صحت است. سرعت (صف فوری ووکامرس و Worker اختصاصی موجودی) مرحله‌های بعدی‌اند.

## نقص‌های اثبات‌شده (پیش از این تغییر)
- **Pull بی نسخه و بی قفل می‌نوشت.** `LMC_Stock_Sync::run` عدد `available` را مستقیم با `apply_stock`
  می‌نشاند. Push نسخه و قفل داشت، ولی Pull نه. پس عکسِ Pullِ کهنه پس از Push تازه، عدد قدیمی را می‌نشاند.
  کنترل منفی: بند ۱ در `stock-ledger-test.php`.
- **کسر محلی ووکامرس در عکس Core نبود.** ووکامرس هنگام سفارش `_stock` را کم می‌کند، ولی Core تا رزرو یا
  فاکتور آن را نمی‌بیند. هر عکس پیش از آن (Pull، یا Push یک فروش حضوری) واحد فروخته‌شده را برمی‌گرداند.
  کنترل منفی: بندهای ۲ و ۴.
- **ACK فقط «HTTP 200» بود.** پاسخ رزرو یا فاکتور نمی‌گفت از کدام حالت انبار به بعد سفارش در عدد Core هست.

مشاهدهٔ `cart.maximum` ۱۱→۱۲→۱۱ اثبات بازنویسی `_stock` نیست. ادعاهای بالا فقط از کد و آزمون قطعی آمده‌اند.

## واترمارک (Core، مهاجرت ۰۹۷)
- `stockRev` همان `inventory.stock_balance.row_version` سطر (تنوع، انبار) است.
- یک Trigger هر تغییر `on_hand` یا `reserved` را **دقیقاً یک واحد** جلو می‌برد، از هر نویسنده‌ای.
  نویسنده‌ای که خودش ۱+ می‌زند هم دو واحد جلو نمی‌رود. نوشتن قانونی زیر قفل سطر است، پس واترمارک
  برای هر سطر به ترتیب Commit یکنواخت است.
- **عدد و واترمارک از یک خواندن می‌آیند:**
  - Push: هر دو در یک `SELECT` و پس از `UPDATE` همان تراکنش.
  - خوراک: `on_hand`، `reserved` و `row_version` از همان سطر.
- **ACK:** پاسخ `POST /web/order-reservations` و `POST /web/orders` برای هر تنوع `stock=[{sku, variationId, stockRev}]` دارد.
  - این واترمارک پس از Commit خوانده می‌شود.
  - معنا: هر عکس آن تنوع با `stockRev ≥` این عدد، اثر سفارش را در خود دارد.
  - واترمارک فقط جلو می‌رود، پس پاسخ Replay هم اثبات معتبر است.

## دفتر کسر و نشاندن (افزونه)
- جدول `lmc_stock_hold(order_id, product_id, qty, ack_rev)`:
  - Hook `woocommerce_reduce_order_item_stock` آن را می‌سازد و `woocommerce_restore_order_item_stock` (لغو) حذفش می‌کند.
  - TTL ندارد؛ کسری که هرگز ACK نگیرد تا تصمیم انسانی کم می‌شود (محافظه‌کار).
- `LMC_Stock_Ledger::apply_snapshot()` تنها مسیر Push و Pull است:
  - هر دو زیر یک قفل MySQL برای هر کالا، با همان نامی که Push از قبل داشت.
  - عکس با `stockRev ≤` آخرین واترمارک نشسته (در همان انبار) رد می‌شود.
- عدد سایت = موجودی Core در عکس − Σ کسرهایی که `ack_rev` آن‌ها تهی یا بزرگ‌تر از `stockRev` عکس است.
  کسرهای با `ack_rev ≤ stockRev` تسویه و حذف می‌شوند.

| رویداد | اثر |
|---|---|
| کسر محلی | سطر تأییدنشده؛ بازمحاسبه از آخرین عکس |
| ACK | اولین `ack_rev` می‌نشیند؛ بازمحاسبه |
| عکس `rev ≤` نشسته | رد (Pull کهنه، Push معوق، تکرار) |
| عکس `rev` تازه، کمتر از `ack_rev` | نشسته، ولی کسر هنوز کم می‌شود؛ واحد فروخته‌شده برنمی‌گردد |
| عکس `rev ≥ ack_rev` | کسر تسویه؛ دوبار کم نمی‌شود |
| لغو | کسر حذف و بازمحاسبه. اگر Core رزرو کرده بود، تا آزادسازی Core کمتر نشان داده می‌شود |

## مرزها و محدودیت‌ها
- **دوبار کم شدن موقت:** اگر عکسِ شامل سفارش پیش از پردازش ACK برسد، تا آمدن ACK یک بار اضافه کم می‌شود.
  این کمتر نشان دادن است، نه فروش بیش از موجودی. بند ۵ آزمون این را می‌سنجد.
- **پاسخ Core قدیمی (بی `stock`):** ACK با واترمارک ۰ ثبت می‌شود. عکس واترمارک‌دار فقط از Core به‌روزشده
  می‌آید و آن پس از این سفارش است.
  - عکس بی `stockRev` مسیر قدیم را زیر همان قفل می‌رود و واترمارک ذخیره‌شده را پاک می‌کند.
- **ارتقای افزونه:** کسرهای تأییدنشدهٔ سفارش‌های فعال (`pending`، `on-hold`، `processing`) پر می‌شوند.
  سفارش تکمیل‌شدهٔ همگام‌نشده یک ناهنجاری قبلی است و حدس زده نمی‌شود.
- **ویرایش دستی قلم سفارش در مدیریت ووکامرس** هنوز کسر را تنظیم نمی‌کند (`wc_maybe_adjust_line_item_product_stock`).
  این کار بعدی است.
- **Pull در قفل مشغول** آن سطر را رد می‌کند و مکان‌نما را جلو نمی‌برد. آزمون واحد مستقیم این شاخه و مسیر
  `stockRev` در `handle_stock` گیرندهٔ Push هنوز آزمون جدا ندارد. منطق مشترک در `stock-ledger-test.php` سنجیده شده.
- **چیزهایی که این مرحله ادعا نمی‌کند:**
  - تضمین صفر فروش اضافه در قطعی؛ رزرو هم‌زمان در Checkout ساخته نمی‌شود.
  - هیچ SLA زمانی.
  - پوشش همهٔ تنظیمات HPOS.

## ترتیب استقرار و برگشت
1. **Core:** مهاجرت ۰۹۷ (فقط Trigger و بازتعریف `push_web_stock`؛ بی تغییر داده، با `lock_timeout = 5s`)، سپس API.
   افزونهٔ قدیم فیلدهای تازه را نادیده می‌گیرد.
2. **افزونه:** جدول با `ensure_schema` روی `plugins_loaded` ساخته و پر می‌شود.
3. **برگشت:**
   - افزونه: جدول بی‌استفاده می‌ماند و رفتار قدیم برمی‌گردد.
   - API: فیلدها حذف می‌شوند، افزونه به مسیر قدیم می‌رود و واترمارک‌ها را پاک می‌کند.
   - مهاجرت ۰۹۷ برنمی‌گردد. Trigger فقط شمارنده را جلو می‌برد.
